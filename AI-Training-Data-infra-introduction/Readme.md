## 1 数据流设计

### 1.1 数据流概述

数据是AI训练的最基本生命线，没有足够的数据，后续的一切都是空谈。海量的数据获取至今为止都是一个比较棘手的问题，网络中开源的数据内容过少，不仅大概率和实际生产中所需要的数据方向不同，更重要的是数据量太少，无法形成一个可靠的训练结果，导致最后训练出的AI更像是对原有数据的过拟合，几乎没有可用性可言。

对于过分缺少的数据，我们需要一个能够获得大量数据的架构设计，这里我们不讨论详细的细节方法，而是更多的在架构设计层面给出解决方案，给出各个数据流中的各个组件，这些组件并不是单独存在的，而是可以构成一个整体，服务于后续的数据飞轮，数据飞轮部分我们将列举实际业务数据飞轮的数据流系统情况，并说明每个方案的缺陷和优点。

这里给出的解决方案和处理流程是经过多层抽象后的可复现结论，而不是直接就能落地的数据流处理系统，当读者在处理真实业务时，应当按照自己的工作内容进行充分的调研和业务分析，而非生搬硬套，避免上线业务事故的发生。

#### 1.1.1 数据来源

数据来源（Data source）在这里我们指的是最原始的数据，甚至可能是无法阅读的Raw Data，数据来源决定了训练数据体量的基础。

AI 训练数据既可以来自外部世界，也可以来自企业内部业务；既可以由人类主动生产，也可以由模型和仿真系统生成。随着模型上线，模型自身的运行结果、用户反馈和失败案例还会形成新的数据来源，使数据流从一次性的采集流水线转变为持续迭代的数据飞轮。

数据来源是多种多样的，尤其是在当今众多互联网ToC企业和有大量优秀开源数据集的处境下。但主要的数据获取途径，更多的还是归类于以下几种情况。

- 公开的互联网数据
    这是目前获得最容易的，覆盖面最广，也是量最大的途径，但是会有版权，风险，一般都会使用爬虫爬取数据。
- 公开数据集
    这种数据集一般包括学术数据集 开源训练集 Benchmark 数据集 行业公开数据集 政府和研究机构开放数据。标准化好，质量相对稳定，但是这些数据领域覆盖有限，规模一般也有限。
- 企业内部业务数据
    这是业务价值最高的一类数据，一般是ToC业务场景中和用户的交互记录，日志等内容。这类数据和业务分布场景最接近，同时也是构建数据飞轮最主要的数据来源。
- 用户反馈数据
    
- 人工生产数据和合成数据
    这些数据不是从现有系统中自然产生，而是由人或者模型专门生成的。这类数据也要分为两类来看，人造数据成本较高，但质量和目标性通常更强，尤其适合监督微调、偏好优化和安全训练，合成数据的优势是成本低、扩展快，但需要警惕错误放大、模式单一和模型自我循环退化
- 仿真与环境交互数据
    这些数据一般是用于机器人、自动驾驶、游戏智能体和 Agent，这类数据不是简单的静态文本，而是： 
    ```
        状态 → 动作 → 环境反馈 → 新状态
    ```
    它对训练 Agent 和决策模型尤其重要
- 第三方数据采购
    它能快速补足特定领域，但需要处理许可范围、数据所有权和使用期限。


#### 1.1.2 数据接入与处理流水线

数据来源决定了原始数据的规模和分布，但原始数据通常无法直接被训练任务使用。公开互联网数据可能包含大量重复内容、广告、乱码和低质量文本；业务数据可能存在结构不统一、敏感信息和上下文缺失；用户交互数据则通常以日志、事件或者数据库记录的形式存在。

因此，在原始数据进入训练系统之后，需要经过一条完整的数据处理流水线，将来源不同、格式不同、质量不稳定的数据，逐步转换成结构统一、质量可控并且能够被后续数据集构建系统消费的数据。

一条典型的训练数据处理流水线如下：

```text
数据来源
   ↓
数据接入
   ↓
原始数据落地
   ↓
解析与格式标准化
   ↓
数据清洗
   ↓
去重与相似数据检测
   ↓
质量过滤
   ↓
安全、隐私与合规处理
   ↓
标注与数据增强
   ↓
Tokenization 与样本打包
   ↓
候选数据集
```

这里的候选数据集并不是最终可以直接用于训练的数据集，而是已经完成基础处理、等待后续进行数据集划分、版本管理和发布的数据集合。

##### 数据接入

数据接入负责将来自不同数据源的数据导入数据基座。不同数据源的数据产生方式不同，因此需要使用不同的接入方式。

数据接入可以分为批处理和流式处理两种方式。

批处理通常按照固定周期导入一批数据，适合互联网数据、历史业务数据和公开数据集等更新频率相对较低的数据。流式处理则会持续接收新产生的数据，适合用户反馈、在线交互日志、模型调用记录和实时业务事件。

在实际系统中，这两种方式往往会同时存在：

```text
离线数据源 ──→ 批量导入 ──┐
                       ├──→ 统一处理流水线
实时数据源 ──→ 流式接入 ──┘
```

无论采用哪种方式，接入层都不应直接修改原始数据。系统通常会首先保存一份未经处理的原始数据，使后续处理过程可以重新执行，也便于问题追踪、数据审计和算法迭代。

##### 解析与格式标准化

不同来源的数据通常具有不同的数据格式，例如 JSON、CSV、Parquet、HTML、PDF、图片、音频、视频、数据库记录或者自定义日志格式。

格式标准化阶段负责将这些异构数据转换为数据基座内部统一的数据表达形式。例如，一条文本训练样本可以被统一表示为：

```json
{
  "id": "sample-id",
  "source": "customer-service",
  "content": "原始文本内容",
  "metadata": {
    "created_at": "2026-07-23",
    "language": "zh",
    "source_uri": "..."
  }
}
```

对于对话数据，通常还需要保留角色、轮次和上下文关系：

```json
{
  "messages": [
    {
      "role": "user",
      "content": "用户输入"
    },
    {
      "role": "assistant",
      "content": "模型回答"
    }
  ]
}
```

格式标准化的目的不是让所有数据拥有完全相同的字段，而是为不同模态和不同任务定义稳定的数据协议，使后续处理组件不需要重复适配每一种上游数据格式。

##### 数据清洗

数据清洗负责删除或者修复原始数据中的明显异常内容，常见操作包括：

* 删除乱码、空文本和无法解析的数据；
* 清除网页中的导航栏、广告和无关 HTML 标签；
* 修复异常编码和字符；
* 统一换行符、空格和标点格式；
* 删除过短、过长或者信息密度过低的内容；
* 识别缺少必要字段的样本；
* 过滤抓取失败页面和错误响应；
* 对音频、图片和视频进行完整性检查。

数据清洗并不等同于质量过滤。清洗主要解决数据是否完整、格式是否正确以及内容是否能够被正常解析的问题，而质量过滤则进一步判断数据是否值得进入训练集。

##### 去重与相似数据检测

重复数据会导致训练数据分布失衡，使模型过度学习某些高频内容，并增加不必要的训练成本。因此，去重通常是大规模训练数据处理中非常重要的一环。

去重可以分为多个层次：

* 完全相同数据的精确去重；
* 对文本标准化之后进行哈希去重；
* 基于 MinHash、SimHash 等方法进行近似去重；
* 基于向量表示检测语义相似数据；
* 在文档内部、数据集内部和不同数据集之间进行交叉去重。

除了训练数据之间的去重，还需要特别关注训练集与验证集、测试集之间的数据泄漏。如果评测数据或者与评测数据高度相似的内容进入训练集，最终得到的评测指标将无法真实反映模型的泛化能力。

##### 数据质量过滤

经过清洗和去重的数据仍然不一定适合作为训练数据。质量过滤负责根据训练目标判断数据的价值。

常见的质量判断维度包括：

* 内容是否完整；
* 信息密度是否足够；
* 语言是否通顺；
* 是否包含大量模板化内容；
* 是否存在事实错误；
* 是否与目标领域相关；
* 是否具有足够的任务难度；
* 是否包含有价值的推理过程；
* 对话是否自然且上下文连贯；
* 模型输出是否真正解决了用户问题。

质量过滤可以通过规则、传统机器学习模型、大语言模型或者人工审核完成。

```text
原始样本
   ↓
规则过滤
   ↓
质量分类模型
   ↓
大模型评分
   ↓
人工抽检
```

规则过滤成本最低，适合删除明显异常数据；质量分类模型适合处理规模较大的数据；大模型评分能够进行更复杂的语义判断，但成本更高，并且可能引入评分模型自身的偏差；人工审核质量最高，但难以覆盖海量数据。

因此，实际系统通常会采用多级过滤机制，先使用低成本方法过滤大部分低质量样本，再对剩余数据使用更高成本的模型或人工进行判断。

##### 安全、隐私与合规处理

公开数据和企业业务数据中可能包含个人信息、商业秘密、违法内容以及受版权保护的内容。在数据进入训练集之前，需要进行专门的安全与合规处理。

常见处理内容包括：手机号，个人信息，密钥等信息。

对于企业内部数据，数据是否具有训练价值和数据是否允许用于训练是两个不同的问题。即使某条数据质量很高，如果没有获得相应授权，也不能直接进入训练集。

##### 数据标注与增强

部分训练数据天然带有标签，例如客服工单的分类结果、用户最终选择的答案或者任务是否执行成功。但大量原始数据并不具备直接用于监督训练的标签，因此需要进行额外的标注。

常见的数据标注形式包括：

* 文本分类标签；
* 实体和关系标注；
* 问题与答案配对；
* 指令与回复构造；
* 多个模型回答之间的偏好排序；
* 安全风险标签；
* 工具调用过程和执行结果；
* Agent 任务是否完成；
* 推理过程是否正确；
* 人工修正后的标准答案。

标注可以由人工、规则系统或者模型完成。人工标注质量通常更容易控制，但成本较高；模型自动标注具有更高的扩展能力，但需要通过人工抽样和自动评测控制错误率。

数据增强则是在已有数据基础上生成新的训练样本。数据增强不能只是简单地扩大数据量。增强后的数据需要保持语义正确，并补充原有数据分布中缺少的场景，否则可能只是在重复模型已经掌握的模式。

##### Tokenization 与样本打包

经过清洗、过滤和标注的数据通常仍然以文本、图片、音频或者结构化对象的形式存在。训练任务真正读取数据之前，还可能需要进行 Tokenization 和样本打包。

对于文本模型，Tokenization 会将文本转换成 Token ID：

```text
原始文本
   ↓
Tokenizer
   ↓
Token ID 序列
```

在此基础上，还需要根据训练方式完成样本构造，例如：

* 添加 BOS、EOS 等特殊 Token；
* 根据对话模板拼接用户和模型消息；
* 生成 Attention Mask；
* 生成监督训练所需的 Label Mask；
* 截断超过最大上下文长度的样本；
* 将多个短样本拼接到同一个训练序列中；
* 按照固定长度或者动态长度进行 Batch 打包；
* 为多模态数据建立文本与图片、音频之间的对应关系。

Tokenization 是否应提前离线完成，需要根据系统设计进行权衡。提前完成可以减少训练时的 CPU 开销，但会使数据与特定 Tokenizer 版本绑定；训练时动态执行更加灵活，但会增加训练数据加载阶段的计算压力。

因此，处理流水线需要记录 Tokenizer 名称、版本、词表和处理参数，避免同一个数据集在不同训练任务中产生不可复现的结果。

##### 流水线的输出

处理流水线的最终输出不是模型，而是一组符合质量要求、具有统一数据协议并附带完整元数据的候选训练样本。

每一条样本除了主要内容外，还应尽可能保留以下信息：

* 数据来源；
* 原始数据标识；
* 接入时间；
* 数据处理版本；
* 清洗和过滤结果；
* 质量评分；
* 标注信息；
* 授权和合规信息；
* Tokenizer 版本；
* 上下游数据血缘。

这些信息将被后续的数据集构建和版本管理系统使用，以完成训练集、验证集和测试集划分，并形成可追踪、可复现的数据集版本。

##### 流水线的工程要求

训练数据处理通常需要面对数量巨大、来源复杂并且持续变化的数据，因此一条可靠的数据流水线还应满足以下工程要求。

**可重复执行**：同一批输入数据在相同处理版本和参数下，应当产生一致的输出结果。

**幂等性**：流水线因故障重新运行时，不应重复生成相同数据或者破坏已经处理完成的结果。

**可追踪性**：每条处理后的数据都应能够追踪到原始来源，以及其经历过的处理步骤和组件版本。

**可观测性**：系统需要记录每个阶段的输入数量、输出数量、过滤比例、失败数量、处理延迟和资源使用情况。

例如：

```text
输入样本：100,000,000
解析失败：  2,000,000
清洗过滤： 15,000,000
重复数据： 25,000,000
质量过滤： 18,000,000
最终保留： 40,000,000
```

**错误隔离**：少量异常数据不应导致整批任务失败。无法处理的数据需要进入独立的错误队列或者隔离区域，等待后续分析和重新处理。

**增量处理**：当上游数据不断更新时，系统应尽量只处理新增或者发生变化的数据，而不是每次重新处理全部历史数据。

**处理逻辑版本化**：清洗规则、过滤模型、提示词、Tokenizer 和标注策略都可能不断发生变化。系统需要记录每个组件的版本，保证数据处理结果可以复现，也能够比较不同处理策略对训练效果的影响。

数据处理流水线连接了原始数据和数据集系统。它解决的是数据如何从不可控的原始状态转变为结构统一、质量可控的候选训练样本。至于各个处理任务由谁触发、如何分配计算资源、失败后如何重试，则属于后续的数据编排部分；候选样本如何划分、发布和形成版本，则属于数据集构建与版本管理部分。


#### 1.1.3 数据编排

数据处理流水线定义了数据需要经历哪些处理步骤，而数据编排（Data Orchestration）负责将这些独立的处理步骤组织成一个可以稳定运行的整体。

在小规模的场景里，数据的处理可能只是运行一些脚本，就可以得到训练的数据，但当数据规模、数据来源和处理任务不断增加后，这种依赖人工执行脚本的方式会逐渐暴露出许多问题，在容灾，中断，竞态等的情况下无法正常工作。

因此，数据编排系统需要将每个处理步骤抽象为独立任务，并明确任务之间的串行关系。

##### 典型数据处理流程

这里我们给出一个最普遍的数据处理流程：

```
数据获取(前文中的数据接入) -> 格式解析 -> 清洗和去重 -> 合规检验，数据分类 -> 数据标注 -> 样本打包 
```

#### 1.1.4 数据集构建与版本管理

经过数据接入、清洗、过滤、标注和增强后，系统得到的是一批候选训练数据。这些数据还需要根据具体训练目标进行选择、组合和划分，最终构建成能够被训练任务直接使用的数据集。

数据集构建与版本管理的核心目标是将分散的候选数据转换为稳定、可追踪、可复现的训练数据产品。

它需要保证知道一个数据集是由哪些数据构成的，知道数据经历了哪些处理，知道某个模型使用了哪个数据集版本，能够复现过去的数据集，能够比较不同数据版本的训练效果，数据出现问题时能够快速定位和回滚。

数据集版本发布后，训练系统便可以根据版本信息读取和消费数据，进入后续的模型训练阶段。

#### 1.1.5 小结

至此，我们的数据流工作已经构建了较为完整的数据处理工作，初步解决了数据清洗和整合工作中存在的问题。

### 1.2 数据飞轮系统

数据飞轮是指系统从真实业务运行中持续获得数据，再通过自动化的数据处理、评估和数据集构建流程，将这些数据转化为新的训练数据，最终用于模型训练和优化的闭环系统。

#### 1.2.1 需求场景

模型进入真实业务后，会持续产生新的数据，例如：

- 用户输入和模型输出；
- 多轮对话记录；
- Agent 工具调用轨迹；
- 任务执行过程和最终结果；
- 用户对结果的修改、接受或拒绝；
- 点赞、点踩和重新生成行为；
- 人工接管和人工修正结果；
- 模型评测结果；
- 低置信度、失败和异常样本。

这些数据与公开数据集不同，它们直接来源于真实业务场景，因此更接近模型实际需要解决的问题。

但是，业务数据本身通常不能直接用于训练。数据中可能包含无效请求、重复内容、敏感信息、错误结果和缺少标签的样本，因此需要通过自动化处理流水线任务完成筛选和转换。

#### 1.2.2 案例：InstructGPT 的人机协同数据飞轮

这里我们以大家现在常用的AI厂商举例，OpenAI的 InstructGPT。这个InstructGPT是基于GPT-3的一个人机协同数据飞轮的案例。

OpenAI 曾使用提交至早期 Playground 产品的用户 Prompt，由标注人员清除其中的个人身份信息，再围绕这些真实使用分布生产两类数据：

1. 标注员编写理想回答，形成监督微调数据；
2. 对多个模型回答进行排序，形成偏好比较数据。

OpenAI 随后用监督数据训练初始模型，用偏好数据训练奖励模型，再通过 PPO 优化语言模型。

```
用户提交的真实 Prompt
        ↓
隐私信息清理
        ↓
标注员编写高质量回答
        ↓
生成监督微调数据集
        ↓
模型生成多个候选回答
        ↓
标注员进行偏好排序
        ↓
生成偏好数据集
        ↓
训练奖励模型和指令模型
```

这个案例并不是完全自动化的数据飞轮，因为其中依赖大量人工标注，但它非常适合说明：企业产品中的真实用户请求，可以反映模型的实际使用分布，并用于构建比通用学术数据集更贴近真实需求的训练数据。


#### 1.2.3 小结

数据飞轮将真实业务、数据处理和模型训练连接成一个持续迭代的闭环。

真实业务持续产生用户请求、模型输出、工具调用轨迹、用户反馈和失败案例。系统通过规则、小模型、LLM 和人工审核，对这些原始数据进行清洗、筛选、标注、评估和增强，将其转化为可以被训练系统使用的数据集。

数据飞轮的价值并不只是降低人工数据处理成本，更重要的是使模型能够持续学习真实业务中不断出现的新问题。最终，业务系统不仅是模型的使用者，同时也成为训练数据的生产者。模型服务业务，业务产生数据，数据继续优化模型，从而形成持续迭代的数据闭环。


## 2 存储架构设计

AI 训练场景中的存储系统，需要同时处理海量训练数据、模型权重、Checkpoint、中间处理结果以及训练日志。与传统业务系统相比，AI 训练具有文件规模大、读取吞吐高、多节点并发访问明显以及计算资源昂贵等特点。

训练任务一旦因为数据读取速度不足而等待，昂贵的 GPU 资源便无法得到充分利用。因此，AI 训练存储系统不仅需要保证数据可靠保存，还需要尽可能降低数据读取对训练过程的阻塞。

这部分是我们全篇最重要的部分，也是AI训练数据基座的核心中的核心。

这里的存储架构设计我们可能更多的倾向于介绍在公司业务场景中，特别是在公司自行进行模型微调或者模型后训练的这种应用场景中的存储架构设计。本文还将结合一个实际的跨云 AI 数据基座，介绍对象存储、JuiceFS、关系型元数据库、GPU 计算节点以及缓存预热系统如何共同组成完整的训练数据访问链路。

### 2.1 存储系统分层抽象

从逻辑职责上看，AI 训练存储系统可以抽象为四层：Training Layer、Filesystem Layer、Cache Layer 和 Remote Storage Layer。

这三层的结构如下图所示：

```
  Training layer
       ｜
  Filesystem Layer
       ｜
    Cache layer
       ｜
Remote Storage layer
```

Training Layer 更多属于 AI Infra 的工作范畴，本文不作重点展开。作为 Data Infra 在 AI 训练场景中的实践总结，本文主要介绍 Filesystem Layer、Cache Layer 和 Remote Storage Layer。

### 2.2 远端存储层（Remote Storage Layer）

Remote Storage Layer 是训练数据基座的最终数据持久化层，负责长期保存原始业务数据，清洗和标注后的中间数据，已发布的训练数据集，模型权重，训练 Checkpoint，评测结果和任务产物。

在本文介绍的架构中，远端存储主要由云厂商提供的对象存储承担。对象存储具有容量扩展简单、数据可靠性高、成本较低和适合保存大规模非结构化数据等特点，因此适合作为 AI 数据基座的最终存储介质。

但是，对象存储与训练程序常用的文件系统接口存在明显差异。训练框架通常希望通过目录、文件路径和随机读取的方式访问数据，而对象存储主要通过对象键和 API 提供访问能力。

因此，Remote Storage Layer 的设计重点不仅是选择对象存储，还应当包括：目录组织，数据分桶，多云数据同步和一致性，单个大文件和海量小文件的访问差异。

对象存储负责数据的持久化和可靠性，但不会单独承担训练节点的高性能数据读取需求。训练节点与对象存储之间仍然需要缓存和文件系统层进行加速。

#### 2.2.1 职责与设计目标

Remote Storage Layer 是 AI 训练数据基座中的持久化存储层。它位于整个训练数据访问链路的底部，负责长期、可靠地保存训练数据、模型权重、Checkpoint 和任务产物，并作为其他缓存副本和计算副本的最终数据来源。

在典型架构中，Remote Storage 通常被视为数据的 Source of Truth。上层缓存中的数据可以被淘汰、失效或者重新构建，但远端存储中的正式数据必须保持完整、可靠且可追踪。

```text
               Source of Truth
                      │
                      ▼
              Remote Storage
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
      节点缓存                 计算节点副本
          │                       │
          └───────────┬───────────┘
                      ▼
                 训练任务消费
```

Remote Storage Layer 的主要职责包括以下几个方面。

##### 数据持久化

Remote Storage 需要长期保存 AI 训练过程中产生的不同类型数据，包括：

* 原始业务数据；
* 清洗、标注和增强后的中间数据；
* 正式发布的训练数据集；
* 模型权重；
* 训练 Checkpoint；
* 评测数据和评测结果；
* 数据处理及训练任务的最终产物。

不同类型的数据具有不同的生命周期和访问频率。正式数据集和最终模型权重通常需要长期保留，而部分中间数据和临时 Checkpoint 可以按照生命周期策略进行清理。

##### 统一数据源

在多集群、多节点或者多云环境中，同一份数据可能产生多个缓存和计算副本。Remote Storage 需要提供统一的数据来源，避免不同计算环境各自维护一套相互独立的数据副本。

```text
                  Remote Storage
                  Dataset v3
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
    GPU 集群 A      GPU 集群 B      数据处理集群
```

训练任务应当绑定明确的数据集版本，而不是依赖某台节点上临时存在的本地文件。即使本地缓存被清空，系统也能够根据远端存储重新恢复数据。

##### 数据可靠性

训练数据和模型权重往往需要较高的可靠性。如果数据丢失，不仅会导致训练任务失败，还可能使已经完成的数据清洗、标注和训练工作无法复现。

因此，Remote Storage 需要具备：

* 数据冗余；
* 故障恢复；
* 数据完整性校验；
* 版本保护；
* 误删除防护；
* 备份与归档；
* 跨可用区或者跨地域容灾能力。

Remote Storage 的设计重点通常不是追求最低的单次访问延迟，而是保证数据在节点、磁盘或部分服务发生故障后仍然可以恢复。

##### 容量扩展

AI 训练数据通常会持续增长。除了原始数据外，清洗结果、数据集版本、模型权重和 Checkpoint 也会不断占用新的存储空间。

Remote Storage 应尽可能支持容量的弹性扩展，使系统不需要频繁迁移已有数据或者重新设计存储集群。

对于自建存储系统，扩容通常意味着增加磁盘和存储节点，并处理数据再平衡；对于托管对象存储，容量管理通常由云厂商完成，使用方主要关注费用、配额和访问性能。

##### 多节点并发访问

训练和数据处理任务通常会同时从多个节点访问相同数据。Remote Storage 需要支持较高的并发读取能力，并避免单个训练任务独占整个存储服务。

需要重点考虑的访问模式包括：

* 多个训练节点读取同一个模型权重；
* 多个 Worker 并行读取不同的数据分片；
* 多个训练任务同时访问同一数据集；
* 数据处理任务持续写入新的中间结果；
* Checkpoint 周期性并发写入。

Remote Storage 不一定直接满足所有高性能访问需求，但必须能够作为缓存未命中时的稳定后端，并承受一定规模的突发请求。

##### 接口与生态兼容

Remote Storage 需要能够被上层数据处理、文件系统和训练框架访问。

常见接口包括：

* S3 兼容 API；
* 云厂商对象存储 SDK；
* HTTP API；
* HDFS 接口；
* NFS 或其他文件访问协议；
* 通过 FUSE、CSI 或分布式文件系统间接访问。

在当前云原生 AI 基础设施中，S3 兼容接口具有较强的通用性。许多数据处理框架和分布式文件系统都可以将兼容 S3 API 的存储服务作为后端。

不过，接口兼容并不代表不同产品的行为完全一致。实际选型时仍需要验证权限机制、分片上传、List 操作、错误处理、限流和一致性语义。

##### 安全与访问控制

Remote Storage 通常保存企业内部数据和模型资产，因此需要提供严格的权限控制。

主要包括：

* 按 Bucket、Prefix 或数据集进行权限隔离；
* 使用临时凭证而不是长期静态密钥；
* 控制训练任务的读写范围；
* 对敏感数据进行加密；
* 记录数据访问日志；
* 限制跨账号和跨云访问；
* 防止训练任务覆盖正式数据；
* 对生产数据和测试数据进行隔离。

训练任务通常只需要读取已发布的数据集，不应默认拥有修改原始数据和历史数据集的权限。

##### 成本控制

Remote Storage 的成本不仅包括存储容量费用，还可能包括：

* API 请求费用；
* 跨地域流量费用；
* 公网或跨云流量费用；
* 数据取回费用；
* 自建存储的机器和磁盘成本；
* 运维、监控和故障处理成本；
* 数据冗余带来的额外容量开销。

对于 AI 训练场景，数据可能会被反复读取。如果每次训练都直接从远端对象存储读取全部数据，网络流量和请求成本可能持续增加。因此，Remote Storage 通常需要与上层缓存系统共同设计。

##### Remote Storage 的设计目标

综合来看，Remote Storage Layer 的主要设计目标可以概括为：

1. **可靠性**：数据发生局部故障后仍然能够恢复；
2. **可扩展性**：能够承载持续增长的数据规模；
3. **统一性**：为不同集群和训练任务提供统一的数据来源；
4. **可追踪性**：能够关联数据来源、版本和生命周期；
5. **兼容性**：可以被主流数据处理和训练系统访问；
6. **安全性**：确保数据只被经过授权的任务使用；
7. **成本可控**：在容量、请求、流量和运维成本之间取得平衡；
8. **可恢复性**：上层缓存或计算副本丢失后可以重新构建。

Remote Storage 的主要目标并不是直接提供类似本地磁盘的低延迟访问，也不一定需要完整支持 POSIX 文件系统语义。低延迟读取、文件目录抽象和重复数据访问加速，通常由上层 FileSystem Layer 和 Cache Layer 负责。

---

#### 2.2.2 对象存储类型与选型标准

对象存储是 Remote Storage Layer 中最常见的实现方式之一。它通常使用 Bucket 组织数据，并通过唯一的 Object Key 标识每个对象。

与传统文件系统不同，对象存储主要围绕对象的上传、下载、删除和查询提供能力，而不是直接提供完整的文件目录、随机写入和文件锁语义。

```text
Bucket
├── raw/web/2026/07/data-001.parquet
├── datasets/sft/v3/train-001.parquet
├── models/model-a/v5/model.safetensors
└── checkpoints/job-1024/step-5000/
```

根据部署和维护方式，对象存储可以分为云厂商托管对象存储和自建对象存储两类。

##### 云厂商托管对象存储

托管对象存储由云厂商负责底层存储节点、数据冗余、容量扩展和服务可用性。使用方通常只需要创建 Bucket、配置权限，并通过 API 或 SDK 访问数据。

常见服务包括：

| 类型    | 常见服务示例                                            |
| ----- | ------------------------------------------------- |
| 国际云厂商 | Amazon S3、Google Cloud Storage、Azure Blob Storage |
| 国内云厂商 | 阿里云 OSS、火山引擎 TOS、腾讯云 COS、华为云 OBS                  |

托管对象存储的主要优点包括：

* 不需要自行管理磁盘和存储节点；
* 容量可以按需增长；
* 通常具有较完善的数据冗余和容灾能力；
* 与云厂商的计算、权限和网络体系集成较好；
* 支持生命周期、版本控制和跨地域复制等功能；
* 适合团队运维资源有限的场景。

其主要限制包括：

* 长期使用可能产生较高的存储和请求费用；
* 跨区域和跨云访问可能产生较高流量成本；
* 性能受到云厂商限流、网络和服务配额影响；
* 容易形成对特定云厂商的依赖；
* 部分高级能力和权限模型存在产品差异；
* 业务无法直接控制底层存储节点和数据布局。

对于主要运行在单一云厂商上的训练集群，使用同一云厂商的对象存储通常能够降低网络复杂度和跨云流量成本。

##### 自建对象存储

自建对象存储由企业自行部署和维护。常见方案包括：

* MinIO；
* Ceph RGW；
* 其他提供 S3 兼容接口的分布式存储系统。

自建对象存储的主要优点包括：

* 可以控制数据实际存放的位置；
* 可以根据业务需求选择磁盘、网络和冗余策略；
* 适合本地数据中心、私有云或合规要求较高的场景；
* 在数据量稳定且访问频繁时，可能降低长期云服务费用；
* 可以减少对单一云厂商的依赖；
* 能够在本地高速网络中为计算集群提供数据服务。

其主要限制包括：

* 需要自行管理磁盘、节点、扩容和故障恢复；
* 需要持续维护监控、告警、升级和容量规划；
* 存储节点故障可能触发较大规模的数据恢复；
* 扩容和数据再平衡会消耗网络及磁盘资源；
* 数据可靠性取决于实际部署和运维水平；
* 小规模集群可能无法充分发挥分布式存储的优势。

自建对象存储并不代表一定比云对象存储成本更低。如果数据规模较小、团队缺少存储运维经验或者计算资源本身具有较强弹性，自建存储的机器和人力成本可能高于托管服务。

##### 托管对象存储与自建对象存储的基本比较

| 维度     | 托管对象存储           | 自建对象存储           |
| ------ | ---------------- | ---------------- |
| 容量扩展   | 通常自动扩展           | 需要增加节点和磁盘        |
| 运维成本   | 较低               | 较高               |
| 底层控制能力 | 较弱               | 较强               |
| 初期建设成本 | 较低               | 较高               |
| 长期成本   | 与容量、请求和流量相关      | 与硬件、机房和人力相关      |
| 数据位置   | 由云服务区域决定         | 可以自行控制           |
| 故障处理   | 主要由云厂商负责         | 由使用方负责           |
| 云生态集成  | 较好               | 需要自行适配           |
| 跨云能力   | 可能受流量和产品绑定影响     | 接口可控，但仍需建设同步链路   |
| 适用场景   | 云上业务、快速上线、有限运维团队 | 私有化、本地集群、强数据控制需求 |

##### 对象存储的选型维度

对象存储选型不能只比较存储单价或厂商品牌，而应当从实际工作负载出发进行分析。

###### 数据规模与增长速度

首先需要估算：

* 当前数据总量；
* 每日或每月新增数据量；
* 数据保留周期；
* 数据集版本数量；
* Checkpoint 和模型权重的增长速度；
* 是否需要保存多个副本。

如果数据规模增长较快，应优先考虑容量扩展简单、生命周期管理完善的方案。

###### 对象数量与平均大小

相同的数据总量可能对应完全不同的存储压力：

```text
场景 A：1 PB 数据，由 1,000 个大对象组成
场景 B：1 PB 数据，由 10 亿个小对象组成
```

大量小对象会增加：

* 请求数量；
* List 和元数据操作压力；
* 网络连接开销；
* 文件系统映射成本；
* 数据扫描和同步复杂度。

因此，选型时不仅要关注容量，还要关注对象数量、平均大小和大小分布。

###### 访问模式

需要明确数据主要以何种方式被访问：

* 大文件顺序读取；
* 小文件随机读取；
* 多节点并发读取；
* 数据写入一次、读取多次；
* 频繁覆盖和更新；
* 按数据集版本整体读取；
* 只读取对象中的部分范围；
* 周期性写入 Checkpoint。

对象存储更适合对象级别的写入和读取，不适合频繁修改同一对象中的少量内容。需要高频随机写入的场景，可能需要引入文件系统、块存储或专门的中间存储层。

###### 性能与网络距离

需要评估对象存储与计算集群之间的网络关系：

```text
同地域同云访问
同云跨地域访问
跨云访问
公网访问
本地数据中心访问云对象存储
```

距离越远，通常意味着更高的延迟、更低的稳定吞吐以及更高的流量成本。

对于训练任务而言，需要重点验证：

* 单节点读取吞吐；
* 多节点聚合吞吐；
* 首字节延迟；
* 并发请求能力；
* 大文件读取性能；
* Range Read 性能；
* 训练高峰期的稳定性；
* 服务限流和配额。

###### 可靠性与容灾需求

需要明确系统可以容忍的数据丢失范围和恢复时间，例如：

* 是否允许单个可用区故障影响训练；
* 是否需要跨地域副本；
* 是否需要对象版本控制；
* 是否需要防止误删除；
* 数据损坏后如何发现；
* 是否需要离线备份；
* 需要多长时间完成数据恢复。

并非所有数据都需要相同等级的保护。正式数据集和最终权重可以使用较高可靠性策略，而可以重新生成的中间数据可以采用成本更低的存储策略。

###### 一致性与数据可见性

对象写入完成后，训练任务何时能够读取到新数据，是数据集发布流程中的重要问题。

选型时需要验证：

* 新对象写入后的可见性；
* 对象覆盖后的读取行为；
* 删除操作的传播；
* List 结果是否及时更新；
* 跨地域复制的延迟；
* 多云同步完成后如何确认数据就绪。

在训练数据基座中，通常不应只依赖“文件已经出现”来判断数据集可以使用，而应通过 Manifest、版本状态或发布标记确认整个数据集已经完整写入。

###### 接口和生态兼容性

需要检查对象存储是否能够被现有系统稳定访问，例如：

* 是否兼容 S3 API；
* 是否支持当前使用的数据处理框架；
* 是否可以作为 JuiceFS 等文件系统的数据后端；
* 是否支持 Kubernetes CSI 或相应挂载方式；
* SDK 是否覆盖主要开发语言；
* 是否支持 Multipart Upload 和 Range Read；
* 权限、签名和临时凭证是否容易集成。

S3 兼容性需要通过实际测试确认，不能只根据产品声明判断。

###### 安全与合规

对于企业业务数据，需要考虑：

* 数据是否允许进入公有云；
* 数据必须保存在哪个地域；
* 是否需要服务端或者客户端加密；
* 是否需要审计日志；
* 是否支持细粒度权限；
* 是否支持密钥托管；
* 是否需要私网访问；
* 是否需要隔离不同业务和租户。

如果数据具有严格的本地保存要求，自建对象存储或者私有化部署可能比公共云服务更合适。

###### 成本

完整成本应包括：

```text
总成本 =
存储容量费用
+ 请求费用
+ 数据读取费用
+ 跨区域或跨云流量费用
+ 缓存成本
+ 存储节点成本
+ 运维人力成本
+ 故障恢复成本
```

托管对象存储的费用通常更容易在早期控制，但随着数据量、请求量和跨云流量增长，长期费用可能显著增加。

自建对象存储可以减少部分云服务费用，但会引入服务器、磁盘、网络、机房和运维成本。两种方案需要基于较长周期的总拥有成本进行比较。

##### 基本选型原则

对象存储不存在适用于所有场景的统一最优解，可以按照以下原则进行初步选择：

```text
云上业务、快速上线、运维能力有限
→ 优先考虑云厂商托管对象存储

私有化部署、数据不能离开本地
→ 考虑自建对象存储

计算集群和数据位于同一云
→ 优先选择同云同地域的对象存储

存在多个云计算集群
→ 明确主数据源，并建设复制和版本就绪机制

数据被频繁重复读取
→ 在远端存储之上增加文件系统和缓存层

存在海量小文件
→ 优先优化数据格式和打包方式，再评估文件系统抽象
```

对象存储选型的本质不是选择功能最多的产品，而是在可靠性、性能、成本、运维复杂度、生态兼容和数据控制能力之间进行权衡。

选型结果还需要通过实际业务数据进行验证，尤其是多节点并发读取、大文件和小文件访问、跨云传输以及缓存未命中场景下的性能表现。

#### 2.2.3 对象存储的部署形态与访问方式

对象存储可以按照部署方式分为云厂商托管对象存储和企业自建对象存储。无论采用哪种部署方式，上层应用通常都通过对象存储 API、SDK 或者文件系统抽象层访问其中的数据。

##### S3 API 直接访问

S3 API 是当前对象存储中较为通用的访问接口。应用程序可以通过 SDK、命令行工具或者 HTTP 请求直接执行对象的上传、下载、查询和删除操作。

```text
训练或数据处理程序
        ↓
    S3 SDK / API
        ↓
      对象存储
```

直接通过 S3 API 访问对象存储具有链路简单、依赖较少和适合批量数据处理等优点。Ray Data、Spark 和部分训练框架可以直接读取对象存储中的数据。

但是，对象存储 API 与传统文件系统接口存在差异。部分依赖 POSIX 文件路径、随机访问、目录操作或者文件锁的程序，通常无法直接使用对象存储，需要通过文件系统层进行适配。

##### 云厂商托管对象存储

云对象存储由云厂商负责底层硬件、容量扩展、数据冗余和故障恢复。常见服务包括 Amazon S3、阿里云 OSS、火山引擎 TOS 和腾讯云 COS。

云对象存储适合以下场景：

* 训练和数据处理任务主要运行在公有云中；
* 数据规模持续增长；
* 团队不希望自行维护存储集群；
* 需要较高的数据可靠性和可用性；
* 需要使用生命周期、版本控制和跨地域复制等能力。

在单云环境中，计算集群通常优先选择同地域的对象存储，以减少网络延迟和跨地域流量成本。

##### MinIO

MinIO 是一种提供 S3 兼容接口的对象存储系统，可以部署在企业自己的服务器、裸金属集群或者 Kubernetes 环境中。

MinIO 的优势是部署方式相对直接，并且能够为本地计算集群提供统一的 S3 访问接口。它适合私有化部署、本地数据中心以及需要自行控制数据位置的场景。

但是，自建 MinIO 需要企业自行承担：

* 磁盘和存储节点管理；
* 数据冗余；
* 容量扩展；
* 故障恢复；
* 监控和告警；
* 软件升级；
* 数据备份。

因此，在缺少独立存储节点或者存储运维能力有限的场景中，自建 MinIO 不一定比使用云对象存储更合适。

##### Ceph RGW

Ceph 是一种分布式存储系统，可以提供块存储、文件存储和对象存储能力。其中，Ceph RGW，即 RADOS Gateway，负责向上层提供兼容 S3 或 Swift 的对象存储接口。

```text
应用程序
    ↓
S3 API
    ↓
Ceph RGW
    ↓
Ceph RADOS 存储集群
```

Ceph RGW 适合已经建设 Ceph 集群，或者同时需要块、文件和对象存储能力的企业。相比单独部署对象存储，Ceph 能够提供更加完整的分布式存储体系，但其部署、扩容、故障恢复和日常运维也更加复杂。

因此，Ceph RGW 通常更适合具有较大数据规模、稳定基础设施和专业存储运维团队的场景。

不同部署形态可以简单概括为：

```text
快速上线、降低运维成本
→ 云厂商托管对象存储

私有化部署、需要 S3 兼容接口
→ MinIO

已有 Ceph 基础设施或需要统一存储体系
→ Ceph RGW
```

对象存储的部署方式并不直接决定训练任务最终采用的访问接口。训练程序既可以通过 S3 API 直接读取对象，也可以通过 JuiceFS 等文件系统层间接访问对象存储。

#### 2.2.4 对象键组织、命名空间与数据分桶

对象存储通常使用 Bucket 作为顶层数据容器，并使用 Object Key 唯一标识其中的每一个对象。

对象存储并不存在与传统文件系统完全相同的真实目录。用户看到的目录结构，通常是由 Object Key 中的前缀模拟出来的。

例如：

```text
s3://ai-data/datasets/sft/v3/train-0001.parquet
```

其中：

```text
ai-data
→ Bucket

datasets/sft/v3/
→ Object Key Prefix

train-0001.parquet
→ 对象名称
```

合理的数据组织方式能够降低权限管理、数据同步、生命周期管理和问题排查的复杂度。

##### 数据分桶

不同类型、不同权限或者不同生命周期的数据可以使用不同的 Bucket 进行隔离。例如：

```text
ai-raw-data
→ 原始业务数据

ai-processed-data
→ 清洗和标注后的中间数据

ai-datasets
→ 正式发布的训练数据集

ai-models
→ 模型权重和 Tokenizer

ai-checkpoints
→ 训练 Checkpoint
```

是否需要拆分多个 Bucket，应根据以下因素决定：

* 数据权限是否不同；
* 数据生命周期是否不同；
* 是否由不同团队维护；
* 是否需要独立配置访问策略；
* 是否需要跨云同步；
* 是否需要分别统计容量和成本。

Bucket 数量不宜无限增加。对于权限和生命周期相近的数据，也可以放在同一个 Bucket 中，通过不同 Prefix 进行逻辑隔离。

##### 对象键与命名空间

Object Key 应尽量能够表达数据的业务类型、版本和时间范围。例如：

```text
datasets/
└── customer-service-sft/
    └── v3/
        ├── train/
        │   ├── part-0001.parquet
        │   └── part-0002.parquet
        ├── validation/
        └── test/
```

模型权重可以按照模型名称和版本进行组织：

```text
models/
└── customer-service-model/
    └── v5/
        ├── config.json
        ├── tokenizer.json
        └── model-00001.safetensors
```

Checkpoint 则可以按照训练任务和训练步骤组织：

```text
checkpoints/
└── training-job-1024/
    ├── step-1000/
    ├── step-2000/
    └── step-3000/
```

设计命名空间时，应尽量满足以下要求：

* 路径含义清晰；
* 数据集版本明确；
* 临时数据与正式数据隔离；
* 不直接覆盖已经发布的版本；
* 便于按 Prefix 设置权限；
* 便于执行批量同步和生命周期清理；
* 不在对象键中保存密码、用户隐私等敏感信息。

对于正式数据集，通常应采用不可变版本设计。数据集发布后不再直接修改原有对象，而是生成新的版本：

```text
datasets/sft/v1/
datasets/sft/v2/
datasets/sft/v3/
```

这样可以避免训练过程中读取到正在发生变化的数据，也有利于训练复现、问题定位和版本回滚。

在多云场景中，稳定的 Bucket 与 Object Key 规范还可以作为不同对象存储之间的数据映射基础。同步系统可以根据 Bucket、Prefix 和数据集版本判断需要复制的数据范围，而不需要逐个理解对象的业务内容。

### 2.3 缓存层（Cache Layer）

#### 2.3.1 缓存层概述

Cache Layer 的思想来源于计算机存储体系结构中的金字塔存储体系结构，remote storage最大的问题就是网络带宽非常有限，无法和我们的训练带宽进行良好的匹配。对于这种无法良好匹配可能会导致训练节点空转的情况，行业内形成了一套默契，那就是使用训练节点的本地磁盘作为Cache layer来进行加速。

Cache layer可以让瓶颈由网络带宽变为磁盘IO速度，显而易见，磁盘的IO速度要比网络带宽廉价并且速率也要高非常多。在一些场景中，Cache layer启动速度是OSS对象存储的冷启动速度的八倍，这对与训练加速而言是极大的增强。

但是请务必注意一点，我们Cache layer做的是锦上添花的功能，部分应用场景中，不存在本地磁盘或者其他代替功能（比如虚拟GPU节点），这时候尽管我们可以通过一些方法，比如挂载NAS来实现Cache layer的抽象，但是效果未必良好，所以这里我们的Cache layer如果存在落地效果不好的情况请不要考虑这个解决方案。

请坚信计算机界的名言：“There's no free breakfast”

#### 2.3.2 面向 AI 训练节点集群的分布式缓存

对于高RDMA和同一子网下的多个节点的Cache layer，有一种非常直觉的处理方法：我们能否把这些物理机的Cache layer结合成一个整体？

什么意思呢？

由于我们的cache layer是每个节点的物理磁盘，而这几个机器之间的物理传输速度很快，那么当一个节点拉取了远程对象存储中的内容（比如模型权重）时，我们是否可以让另一个机器在用到这个相同的内容的时候不走远程对象存储，而是直接从别的机器的Cache layer中拉取需要的内容，实现一个更快，更大的Cache layer。

这个思想非常像我们的分布式缓存池，节点先查本地，再从同子网其他缓存节点读取，最后才回源对象存储。

在传统的客户端缓存架构中，每个训练节点只使用自身的内存和本地磁盘缓存数据。

```text
训练节点 A → 本地缓存 A → Remote Storage
训练节点 B → 本地缓存 B → Remote Storage
训练节点 C → 本地缓存 C → Remote Storage
```

这种方式实现简单，并且能够利用本地 SSD 降低重复读取远端存储的开销。但是，各个节点的缓存彼此隔离，同一份模型权重或训练数据可能被多个节点分别从对象存储下载并重复保存。

假设四个训练节点需要加载同一个模型：

```text
节点 A ──→ 对象存储 ──→ 下载模型权重
节点 B ──→ 对象存储 ──→ 再次下载模型权重
节点 C ──→ 对象存储 ──→ 再次下载模型权重
节点 D ──→ 对象存储 ──→ 再次下载模型权重
```

这种架构存在两个问题。

第一，各节点重复保存相同内容，本地磁盘的有效缓存容量受到限制。第二，大量节点同时启动训练任务时，会形成集中回源流量，增加对象存储请求数、网络压力和任务冷启动时间。

对于位于同一子网、节点之间具有高速网络，尤其是具备 RDMA 网络的训练集群，可以采用一种更加适合 AI 工作负载的设计：将多个节点的本地缓存组合成一个逻辑上的分布式缓存池。

```text
                   Remote Storage
                          │
                     缓存未命中
                          ▼
        ┌─────────────────────────────────┐
        │       Distributed Cache Pool    │
        │                                 │
        │ Node A SSD   Node B SSD         │
        │ Node C SSD   Node D SSD         │
        └─────────────────────────────────┘
                          │
                     高速节点网络
                          ▼
                    GPU 训练任务
```

在这种架构下，每台物理机仍然使用自己的本地磁盘保存缓存数据，但缓存节点之间能够相互提供数据。某个节点需要的数据如果已经位于缓存池中的其他节点，就可以通过集群内部高速网络读取，而不必再次访问远端对象存储。

##### 分布式缓存的数据路径

一个简化的分布式缓存读取过程如下：

```text
训练节点发起文件读取
        ↓
确定数据块对应的缓存节点
        ↓
数据块是否已经缓存在缓存池中？
        │
   ┌────┴────┐
   │         │
  是         否
   │         │
   ▼         ▼
从缓存节点   从 Remote Storage
读取数据     下载数据
             ↓
          写入缓存节点
             ↓
        返回给训练任务
```

这里需要区分两种实现思路。

一种是逐级查找：

```text
本地缓存
   ↓ 未命中
查询其他缓存节点
   ↓ 未命中
回源对象存储
```

另一种是通过一致性哈希等方式，预先确定每个数据块应该存放在哪个缓存节点：

```text
数据块标识
   ↓
一致性哈希
   ↓
确定负责该数据块的缓存节点
```

后一种方式不需要依次遍历所有节点。客户端可以直接定位负责该数据块的节点，从而减少缓存查找产生的额外网络通信。

##### 缓存池化的收益

**扩大有效缓存容量**

假设每个节点能够提供 1 TB 本地 SSD，四个节点组成缓存池后，理论上可以形成接近 4 TB 的逻辑缓存空间。

```text
单节点缓存容量：1 TB

四节点缓存池：
1 TB + 1 TB + 1 TB + 1 TB
≈ 4 TB 逻辑缓存容量
```

实际可用容量还会受到缓存副本、淘汰策略、节点容量差异和系统预留空间影响，但相比每个节点重复保存相同数据，缓存池能够提高整体磁盘利用率。

**减少重复回源**

当模型权重或者训练数据已经进入缓存池后，其他节点可以直接从缓存节点读取，从而减少：

* 对象存储 GET 请求；
* 跨云和跨地域流量；
* 多节点重复下载；
* 模型启动时的突发回源；
* 远端存储首字节等待。

这一特性特别适合模型权重、热门数据集和多轮训练等读取频率较高的数据。

**聚合磁盘和网络吞吐**

如果一个文件被拆分成多个数据块，并分布在多个缓存节点上，客户端可以并行从多个节点读取不同的数据块。

```text
模型权重
├── Block 1 → Cache Node A
├── Block 2 → Cache Node B
├── Block 3 → Cache Node C
└── Block 4 → Cache Node D
```

此时，读取吞吐不再只依赖单个节点的磁盘和网卡，而可以利用多个缓存节点的磁盘与网络能力。

**利用高速节点互联**

在普通网络环境中，从其他节点读取缓存仍然需要付出网络传输成本。但当节点之间具有 100 Gbps、200 Gbps 甚至更高带宽的网络时，缓存节点之间的数据传输可能显著快于跨云或远端对象存储访问。

如果进一步使用 RDMA，缓存数据可以减少传统 TCP 协议栈带来的 CPU 中断、上下文切换和内存复制，从而提高高带宽网络的利用率并降低主机 CPU 开销。JuiceFS 企业版已经将 RDMA 应用于分布式缓存的数据传输链路，而元数据和节点发现等控制消息仍通过 TCP 传输。

##### 计算缓存一体与独立缓存集群

分布式缓存可以采用两种部署形态。

第一种是训练节点同时承担缓存职责：

```text
GPU Node A：训练任务 + 本地缓存
GPU Node B：训练任务 + 本地缓存
GPU Node C：训练任务 + 本地缓存
GPU Node D：训练任务 + 本地缓存
```

这种方式能够充分利用物理训练节点已有的 SSD，适合节点相对固定、配置较为一致的裸金属或长期运行集群。

第二种方式是部署独立缓存集群：

```text
动态训练节点
      │
      ▼
固定缓存节点集群
      │
      ▼
Remote Storage
```

独立缓存集群适合训练 Pod 频繁创建和销毁、计算节点弹性伸缩，或者不希望训练进程和缓存服务争抢本地磁盘与网络资源的场景。

JuiceFS 官方也支持独立缓存集群模式。动态计算客户端可以只从缓存组读取数据而不贡献自身缓存，固定节点则负责长期保存和提供缓存数据。

##### JuiceFS 分布式缓存的实现

JuiceFS 企业版提供了分布式缓存能力。启用后，具有相同 Cache Group 配置的客户端会组成一个缓存组。

该缓存组本质上是一个一致性哈希环。文件数据块根据一致性哈希结果分布到不同成员节点，并在组内共享。客户端读取文件时，会根据缓存组拓扑计算数据块对应的缓存节点，并直接向该节点请求数据。

如果对应缓存节点还没有该数据块，则由该节点从对象存储读取，将数据写入自己的缓存盘，再返回给请求方。后续其他客户端再次访问该数据块时，可以直接从缓存组获取，而不必再次回源对象存储。

例如，一个文件由四个数据块组成：

```text
File A
├── a1 → Node A
├── a2 → Node B
├── a3 → Node C
└── a4 → Node D
```

当 Node D 读取 File A 时，它可以从 Node A、Node B 和 Node C 获取对应数据块，并从自身缓存读取 a4。各节点之间的数据传输通过高速内网完成。

因此，JuiceFS 分布式缓存更准确的数据路径是：

```text
客户端读取数据块
        ↓
根据一致性哈希确定所属节点
        ↓
请求对应缓存节点
        ↓
缓存节点命中？
   ┌────┴────┐
   │         │
  命中       未命中
   │         │
   ▼         ▼
返回缓存数据  缓存节点回源对象存储
             ↓
          写入本地缓存
             ↓
          返回数据
```

JuiceFS 社区版主要提供客户端本地缓存；跨节点共享的分布式缓存属于企业版能力。

##### 适用条件

分布式缓存并不适用于所有训练集群。它更适合以下场景：

* 多个节点会重复读取相同模型权重或训练数据；
* 远端对象存储与计算集群之间的链路较慢；
* 存在跨云或跨地域数据访问；
* 节点之间具有高速、稳定且可信的内网或者高速RDMA；
* 每个节点都具有可以用于缓存的本地 SSD；
* 训练集群节点相对稳定；
* 数据读取频率明显高于数据更新频率。

如果数据只会被读取一次，或者节点之间的网络并不比远端存储更快，那么引入分布式缓存可能无法获得足够收益，反而会增加系统复杂度。

##### 工程限制与风险

**缓存节点异构**

如果不同节点的磁盘容量和网络性能差距过大，一致性哈希可能无法充分利用大容量节点，较小或较慢的节点还可能成为尾延迟来源。JuiceFS 官方建议缓存组成员在磁盘容量和网络性能上尽量保持一致。

**缓存节点故障**

缓存只是可重建的临时副本。某个缓存节点故障后，对应数据块需要从对象存储重新读取，因此 Remote Storage 仍然是最终的 Source of Truth。

```text
Remote Storage
→ 权威、可靠、长期副本

Distributed Cache
→ 高性能、可淘汰、可重建副本
```

**缓存穿透**

当多个缓存节点同时不可用、缓存集体失效或者大量新任务同时读取未预热数据时，请求可能集中回源对象存储，形成缓存穿透。

系统需要监控：

* 缓存命中率；
* 节点间读取吞吐；
* 对象存储回源流量；
* 缓存节点磁盘使用率；
* 缓存淘汰速率；
* 缓存节点错误数量；
* 训练任务数据等待时间。

**热点数据块**

当大量客户端同时读取同一个缓存块时，负责该数据块的节点可能成为热点。JuiceFS 提供了将大型缓存组进一步划分为多个子组的能力，以减少单一缓存节点承担过多请求，但代价是不同子组之间可能产生重复缓存。

**资源竞争**

当 GPU 节点同时运行训练任务和缓存服务时，本地磁盘、CPU、内存和网卡可能发生资源竞争。如果训练任务对本地 SSD 的临时读写需求较高，应考虑进行资源限额，或者使用独立缓存节点。

### 2.4 文件系统层（Filesystem Layer）

Remote Storage Layer 主要通过 Bucket、Object Key 和 API 管理数据，而训练框架和普通应用程序通常更习惯通过文件路径访问数据。

例如，训练程序往往希望直接使用：

/data/datasets/sft/v3/train-0001.parquet
/models/model-a/v5/model.safetensors
/checkpoints/job-1024/step-5000/

而不是在业务代码中分别调用不同云厂商的对象存储 SDK。

Filesystem Layer 位于训练任务与底层存储之间，负责将对象存储、分布式存储或者其他远端存储，抽象为统一的文件系统接口。

Filesystem Layer 主要解决以下问题：

- 为训练程序提供统一的文件路径；
- 屏蔽不同对象存储的 API 差异；
- 提供目录、文件和权限等抽象；
- 管理文件元数据和命名空间；
- 支持多个训练节点共享访问同一数据集；
- 将文件读写请求转换为底层对象存储请求；
- 与缓存层协同降低远程访问开销。

#### 2.4.1 文件系统接口与 POSIX 抽象

为了解决统一文件路径和API差异的问题，以及为了方便管理文件内容和读写请求，在主流的FS（FileSystem）中一般都对文件处理功能进行了充分的抽象。比如Read，Write，Rename等。Filesystem Layer 可以向上层提供类似 POSIX 的访问方式。这样可以减少应用程序对对象存储 SDK 的依赖，并降低已有训练代码迁移到云上存储的改造成本。

但是这种系统接口和抽象无法实现像本地一样对文件的处理，比如文件锁，随机读写和一致性事务等的具体问题，需要参考实际文件系统的实现。

#### 2.4.2 文件元数据管理

文件元数据管理一般和文件本身进行隔离保存，虽然这种情况可能会导致文件元数据和文件本身的一致性问题，但是这种隔离方式可以让文件系统本身更注重于文件自身数据的处理。

文件元数据在企业级的文件系统中一般是单独进行RDS实例的购买，同时结合市面上常见的文件系统，形成一个完整的数据存储系统。

企业级文件系统同样还需要注意数据的保存要有容灾的能力，所有一般RDS并非单点，而是采用多点RDS或者RDS备份这种方式。

#### 2.4.3 文件到对象的映射

一个较大的文件在存入一个文件系统中，并不是完整的作为一个整体保存，而是通过切分成片的模式，将文件分散到不同的chunk。

比如一个较大的模型权重文件，一般会进行切分处理：
```
model.weight
├ chunk1
├ chunk2
...
```

当进行文件读取的时候，就会根据偏移值来定位数据块，最后作为一个整体文件来进行读取。

#### 2.4.4 文件系统接入方式

在 Kubernetes 或物理机集群中，文件系统常见的接入方式包括：

- FUSE 挂载；
- CSI 驱动；
- 容器内直接运行客户端；
- client用户态客户端；

FUSE 挂载本身能够提供用户态的文件系统接口和良好的兼容性，但是可能会存在用户态切换的开销。

CSI驱动模式本身更贴合K8s的环境，可以将文件系统作为一个持久化保存卷挂载到pod中，方便K8s集群的管理。

容器内直接运行客户端需要给出版本合适的二进制文件，client用户态客户端可以更加灵活的使用客户端中的功能。两者最大的区别是，容器内一般是在K8s集群管理的时候用的更多，更适合分配任务来进行文件管理，而client用户态的客户端适合更底层并且更接近物理主机的情况。两种情况并非完全冲突，在k8s不管理我们的显卡算力集群的时候，用户态的客户端是一个很好的解决方案，同时当我们购买的算力集群是一些virtual节点的时候，容器内直接运行的客户端有更好的表现和更低的适配成本。

#### 2.4.5 文件系统层的局限

引入文件系统虽然可以解决很多兼容性和访问性的问题，但是同样会带来元数据服务和额外访问的开销。因此，Filesystem Layer 并不是对象存储的替代品，而是一层面向上层应用的访问抽象。

### 2.4小结

Filesystem Layer 将对象存储中的对象转换为训练程序能够直接使用的文件和目录，并提供统一命名空间、元数据管理和多节点共享访问能力。
```
对象存储
   ↓
文件与对象映射
   ↓
统一命名空间
   ↓
POSIX 文件接口
   ↓
训练任务
```
它主要解决的是应用兼容性和数据管理问题，而 Cache Layer 主要解决访问性能问题，Remote Storage 则负责最终的数据可靠性和持久化。

三者共同组成完整的数据访问链路：
```
Training Layer
      ↓
Filesystem Layer
提供统一文件接口与命名空间
      ↓
Cache Layer
降低远程读取开销
      ↓
Remote Storage Layer
提供可靠、可扩展的持久化存储
```

### 2.5 基于 JuiceFS 的 AI 训练存储基座实践

前面分别介绍 Remote Storage、Cache 和 Filesystem 的逻辑职责；本节通过 JuiceFS 展示这些能力如何在真实系统中组合起来。

#### 2.5.1 业务背景与系统约束

在我们这个章节中的业务背景，是基于AI训练的存储基座。

对于这种AI训练特化的存储基座，最常用的存储系统，就是JFS。

JFS本身提供了灵活并且统一的存储结构，支持多种不同存储部分的结合，一个文件系统既可以有本地磁盘做成的MinIO，也能够同时容纳主流的对象存储，如OSS和TOS等。

#### 2.5.2 整体架构与数据访问路径

JuiceFS 采用数据与元数据分离的架构。文件内容被切分为数据块并持久化到对象存储中，文件名、目录结构、权限、文件大小以及数据块映射关系则由独立的元数据服务维护。JuiceFS 客户端位于训练任务与底层存储之间，负责将训练程序发起的文件操作转换为元数据请求和对象存储请求。

在本文讨论的生产架构中，整个系统可以抽象为以下几个部分：

```text
                       训练任务
                 DataLoader / Framework
                           │
                           ▼
                    JuiceFS 客户端
          ┌────────────────┼────────────────┐
          │                │                │
          ▼                ▼                ▼
     文件系统接口       本地/分布式缓存      元数据请求
          │                │                │
          └──────────┬─────┘                ▼
                     │                 元数据服务
                     ▼                 RDS / DB
                对象存储后端
                 OSS / TOS
```

其中：

* 对象存储负责保存实际文件数据，是数据内容的最终持久化位置；
* 元数据服务负责维护文件系统的命名空间和文件到对象之间的映射；
* JuiceFS 客户端向训练程序提供统一的文件系统接口；
* 本地缓存和分布式缓存负责减少训练节点重复访问对象存储；
* Kubernetes 负责训练任务、挂载客户端和缓存资源的调度；
* 监控系统负责采集文件系统、数据库、对象存储、磁盘和网络状态。

以读取一个模型权重文件为例，完整访问路径如下：

```text
训练程序打开模型权重文件
          ↓
JuiceFS 客户端查询文件元数据
          ↓
确定文件对应的数据块
          ↓
查询本地或分布式缓存
          ↓
缓存命中？
   ┌──────┴──────┐
   │             │
  命中           未命中
   │             │
   ▼             ▼
读取缓存数据    从对象存储读取
                   ↓
                写入缓存
                   ↓
             返回给训练程序
```

对于写入操作，JuiceFS 客户端负责接收训练程序写入的数据，将数据组织为底层对象，并同步更新元数据服务中的文件信息。

```text
训练任务写入文件
        ↓
JuiceFS 客户端接收写入
        ↓
生成并上传数据块
        ↓
更新文件元数据
        ↓
文件对其他客户端可见
```

需要注意，前文中的 Remote Storage Layer、Filesystem Layer 和 Cache Layer 是逻辑职责上的分层。在具体实现中，JuiceFS 客户端同时承担了文件系统接口、对象映射、本地缓存和部分控制逻辑，因此同一个产品可能横跨多个逻辑层。

---

#### 2.5.3 对象存储后端设计

在具有实体训练节点并使用云对象存储的场景中，对象存储应当作为训练数据、模型权重和任务产物的最终持久化位置，而训练节点本地磁盘只承担临时缓存职责。

```text
                    对象存储
                 Source of Truth
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
      训练节点 A      训练节点 B      训练节点 C
      本地缓存        本地缓存        本地缓存
```

训练节点发生故障、本地磁盘被清理或者缓存被淘汰后，文件系统仍然能够从对象存储重新构建缓存。相反，正式数据不应只保存在某台训练机的本地磁盘中。

对象存储后端应重点处理以下问题。

##### 网络位置

当训练节点和对象存储位于同一云厂商、同一地域时，应优先使用对象存储的内网 Endpoint。相比公网访问，内网链路通常能够提供更低的访问延迟，并避免不必要的公网流量费用。JuiceFS 官方也建议在创建文件系统时优先配置内网 Endpoint。

当实体训练机位于本地机房或者另一云环境时，需要根据实际情况选择：

* 专线或云企业网；
* 跨云私网链路；
* 公网加密访问；
* 在计算侧建立对象存储副本；
* 通过缓存预热减少跨云重复传输。

如果训练节点长期跨云读取远端对象存储，通常应优先考虑数据复制，而不是把所有性能问题都交给缓存层解决。

##### 权限管理

训练节点访问对象存储时，应优先使用实例角色、RAM Role、IAM Role 或短期临时凭证，而不是在配置文件中长期保存 Access Key 和 Secret Key。JuiceFS 支持通过云角色或临时凭证访问对象存储，并支持在客户端运行期间更新临时凭证。

不同用途的数据应使用不同的权限边界：

```text
训练数据集
→ 训练任务只读

Checkpoint 目录
→ 当前训练任务可读写

模型发布目录
→ 只有发布任务可写

原始业务数据
→ 普通训练任务不可直接访问
```

##### 数据组织

对象存储中的数据应按照类型和版本进行组织，例如：

```text
raw/
processed/
datasets/
models/
checkpoints/
evaluation/
```

正式数据集和模型版本应尽量采用不可变设计。已经发布的版本不直接覆盖，而是创建新的版本目录：

```text
datasets/sft/v1/
datasets/sft/v2/
datasets/sft/v3/
```

这种方式能够降低训练过程中读取到半成品数据的风险，并为跨云同步、回滚和训练复现提供稳定边界。


---

#### 2.5.4 元数据服务设计

JuiceFS 将实际文件内容保存在对象存储中，将目录、文件名、权限、大小和数据块映射等信息保存在元数据服务中。对于自托管或社区版部署，可以使用 PostgreSQL、MySQL、Redis 等数据库作为 Metadata Engine。

本文假设使用云厂商托管的关系型数据库服务作为元数据引擎。

```text
JuiceFS Client
      │
      ▼
RDS 主实例
      │
      ├── 主备复制
      ├── 自动备份
      ├── 时间点恢复
      └── 监控与告警
```

##### 高可用设计

元数据数据库应采用单一逻辑主库加高可用备库的形式，而不是将元数据表任意拆分到多个数据库分片中。

JuiceFS 的元数据操作依赖数据库事务保证原子性。以 PostgreSQL 为例，JuiceFS 官方不建议使用需要跨分片事务的多服务器分布式架构，因为 PostgreSQL 无法为此类元数据操作提供完整的多分片事务能力。

因此，更合适的设计通常是：

* 单一逻辑主实例；
* 同地域或跨可用区主备；
* 数据库故障时自动切换；
* 客户端通过固定连接地址访问；
* 避免在数据库层对元数据进行业务分片。

高可用主要解决数据库实例故障后的服务恢复问题，但不能替代数据备份。

##### 备份与恢复

元数据一旦丢失，即使对象存储中的文件数据仍然存在，系统也可能无法恢复原来的文件名、目录和数据块映射关系。

因此，应同时建设：

* RDS 自动备份；
* 时间点恢复；
* 周期性逻辑备份；
* 异地备份；
* 恢复演练；
* 备份可用性检查。

备份的关键不只是“已经创建”，而是需要定期验证能否在新的数据库实例中恢复，并确认恢复后的 JuiceFS 能够正确挂载和访问文件。

##### 性能与连接管理

元数据数据库应与主要训练集群保持较低网络延迟。虽然大文件内容不会经过元数据数据库，但打开文件、查询目录和获取文件属性都需要访问元数据服务。

在海量小文件场景中，元数据请求可能比对象存储吞吐更早成为瓶颈。

需要重点监控：

* 数据库 QPS；
* 连接数；
* 事务延迟；
* 慢查询；
* CPU 和内存；
* 磁盘 IOPS；
* 主备复制延迟；
* 故障切换次数。

如果训练任务会在短时间内启动大量客户端，还需要控制数据库连接数量，避免挂载风暴耗尽连接资源。

#### 2.5.5 Kubernetes 与训练节点接入

在 Kubernetes 环境中，可以使用 JuiceFS CSI Driver 将文件系统作为 PersistentVolume 提供给训练 Pod。

在 JuiceFS 中，一个 Volume 对应一个文件系统，访问凭证通常保存在 Kubernetes Secret 中。应用通过 StorageClass、PersistentVolume 和 PersistentVolumeClaim 使用对应文件系统。

```text
训练 Pod
   │
   ▼
PVC
   │
   ▼
JuiceFS CSI Driver
   │
   ▼
Mount Pod / JuiceFS Client
   │
   ├── 元数据服务
   ├── 本地缓存
   └── 对象存储
```

训练任务只需要在 Pod 中声明挂载路径：

```text
/data/datasets
/models
/checkpoints
```

而不需要在训练代码中直接处理对象存储 SDK、Bucket Endpoint 或访问凭证。

##### 训练任务的接入流程

一条典型的训练任务启动链路如下：

```text
提交训练任务
      ↓
Kubernetes 调度训练 Pod
      ↓
CSI Driver 创建或复用 Mount Pod
      ↓
JuiceFS 客户端挂载文件系统
      ↓
检查数据集和模型版本
      ↓
执行缓存预热
      ↓
训练任务进入 Ready
      ↓
开始训练
```

JuiceFS 客户端实际运行在 Mount Pod 中，因此本地缓存、挂载参数以及缓存预热通常也围绕 Mount Pod 进行配置。

##### 权限隔离

训练任务使用的不同目录应采用不同权限：

```text
/datasets
→ 只读挂载

/models
→ 只读或按模型发布流程控制写入

/checkpoints
→ 当前训练任务可读写

/tmp
→ 使用节点本地临时空间
```

正式数据集尽量采用只读挂载，避免训练代码意外修改数据。

##### 调度与缓存亲和性

当使用训练节点本地 SSD 作为缓存时，训练 Pod 的调度位置会影响缓存命中。

同一个任务如果重启后被调度到另一台节点，可能无法直接复用原节点的本地缓存。因此可以根据需求采用：

* Node Affinity；
* 固定训练节点；
* StatefulSet；
* 独立缓存集群；
* JuiceFS 分布式缓存；
* 在任务启动前重新预热。

对于频繁创建和销毁的弹性 Pod，将长期缓存职责放在固定缓存节点上，通常比依赖每个短生命周期 Pod 的本地缓存更加稳定。

#### 2.5.6 本地缓存与缓存预热

当 JuiceFS 客户端第一次读取某个文件时，如果数据尚未进入缓存，需要从对象存储下载对应数据块。

```text
第一次读取
训练任务 → JuiceFS → 对象存储 → 本地缓存

后续读取
训练任务 → JuiceFS → 本地缓存
```

对于模型权重和训练数据集，冷缓存读取可能显著增加任务启动时间。因此，在训练正式开始前，可以主动执行缓存预热。

##### 缓存预热流程

```text
训练任务提交
      ↓
确定模型和数据集版本
      ↓
执行 JuiceFS Warmup
      ↓
将目标文件读取到缓存
      ↓
检查预热状态
      ↓
训练任务开始
```

在 Kubernetes CSI 场景中，由于 JuiceFS 客户端运行在 Mount Pod 中，缓存预热需要在 Mount Pod 内执行；使用 JuiceFS Operator 时，也可以通过 WarmUp 自定义资源声明一次性或周期性预热任务。

##### 预热对象选择

并非所有数据都需要预热。更适合提前进入缓存的数据包括：

* 即将加载的模型权重；
* 当前训练任务使用的数据分片；
* 多个任务反复使用的热门数据集；
* 评测任务共享的基础模型；
* 跨云读取成本较高的数据。

如果缓存容量有限，应优先保证当前任务启动阶段必需的数据，而不是盲目预热整个存储空间。

##### 缓存生命周期

本地缓存是可淘汰、可重建的数据副本，不承担最终持久化责任。

缓存管理需要考虑：

* 缓存目录所在磁盘；
* 最大缓存容量；
* 磁盘剩余空间；
* 数据淘汰策略；
* 多任务之间的缓存竞争；
* 训练临时文件与缓存磁盘的资源隔离；
* 节点重启后的缓存恢复成本。

如果缓存盘同时被容器运行时、训练临时文件和 JuiceFS 使用，需要提前设置容量和 I/O 边界，避免训练任务和缓存互相挤占资源。

#### 2.5.7 分布式缓存与 RDMA 加速

对于具有多台固定物理训练节点的集群，可以进一步将各节点的本地缓存组合为一个分布式缓存池。

```text
                 对象存储
                    │
             缓存未命中时回源
                    ▼
      ┌───────────────────────────┐
      │ JuiceFS Distributed Cache │
      │ Node A SSD + Node B SSD   │
      │ Node C SSD + Node D SSD   │
      └───────────────────────────┘
                    │
              高速节点网络
                    ▼
                 训练任务
```

JuiceFS 企业版的分布式缓存使用缓存组组织多个缓存节点。客户端能够定位数据块所在的缓存节点，并优先通过集群内部网络读取；如果数据块尚未被缓存，则由负责节点从对象存储回源。

##### RDMA 是什么

RDMA，即 Remote Direct Memory Access，是一种允许一台机器通过网络直接访问另一台机器内存的技术。

传统 TCP 数据传输通常需要经过操作系统网络协议栈，并产生 CPU 中断、上下文切换以及用户态和内核态之间的数据复制。RDMA 将大部分数据传输工作交给网卡硬件完成，可以降低 CPU 参与程度和传输延迟。

```text
传统 TCP：
应用内存 → 内核缓冲区 → 网络协议栈 → 网卡

RDMA：
应用内存 → RDMA 网卡 → 远端应用内存
```

JuiceFS 企业版从 5.3 开始支持使用 RDMA 加速客户端与分布式缓存节点之间的数据传输。元数据请求和节点发现等控制消息数据量较小，仍然使用普通 TCP 网络。

##### 生产部署方式

分布式缓存可以采用两种模式。

**训练与缓存一体**

```text
GPU Node A：训练 + 缓存
GPU Node B：训练 + 缓存
GPU Node C：训练 + 缓存
```

适合：

* 固定物理节点；
* 本地 SSD 容量充足；
* 节点配置相对一致；
* 训练任务和缓存可以共享节点资源。

**独立缓存集群**

```text
训练 Pod
    ↓
固定缓存节点
    ↓
对象存储
```

适合：

* 训练 Pod 生命周期较短；
* 计算节点频繁扩缩容；
* 不希望缓存与训练争抢本地磁盘；
* 希望长期保留热门数据缓存。

##### RDMA 的适用前提

RDMA 并不是开启参数后就必然产生收益。它更适合：

* 节点间具有高速 RDMA 网络；
* 数据块较大；
* 分布式缓存吞吐已经受到 TCP 或 CPU 限制；
* 训练任务会大量从其他缓存节点读取数据；
* 节点和网络环境相对稳定。

如果瓶颈仍然位于对象存储、缓存磁盘或元数据数据库，单独引入 RDMA 并不能解决全部问题。

#### 2.5.8 多云数据同步与版本就绪

当训练资源分布在多个云环境中时，直接跨云读取同一个对象存储可能受到带宽、延迟、稳定性和流量费用限制。

更常见的处理方式是确定一个权威数据源，再将需要使用的数据复制到计算集群附近的对象存储中。

```text
主对象存储
Source of Truth
      │
      ├──→ 云 A 对象存储副本
      └──→ 云 B 对象存储副本
```

JuiceFS 企业版提供异步跨云、跨地域对象数据复制能力，但对象数据复制主要改善远端数据访问性能，元数据访问延迟仍然取决于元数据服务和客户端之间的网络距离。

##### 全量同步

全量同步通常用于：

* 第一次建立目标副本；
* 新增一个训练区域；
* 目标存储数据丢失；
* 重新构建整个数据集副本。

全量同步成本较高，因此不适合频繁执行。

##### 增量同步

在完成第一次全量复制后，日常同步应尽量只传输新增或发生变化的数据。

增量同步可以依据：

* 文件修改时间；
* 对象 ETag 或校验值；
* 数据集 Manifest；
* 数据集版本；
* 上一次同步游标；
* 对象存储事件；
* 文件系统变更日志。

对于训练数据，推荐采用不可变版本。新版本只新增对象，不直接覆盖旧版本，从而降低增量同步和冲突处理的复杂度。

##### 事件触发同步

事件触发同步是指某个业务事件发生后立即执行同步，例如：

* 数据集完成发布；
* 新模型权重生成；
* 人工要求将指定目录同步到另一云；
* 新训练任务即将启动；
* 某个评测任务需要指定模型版本。

```text
数据集发布事件
      ↓
创建同步任务
      ↓
复制对应版本
      ↓
执行校验
      ↓
标记目标版本就绪
```

事件触发方式具有较低的数据等待时间，但需要保证事件重复发送时同步任务仍然具有幂等性。

##### 定时同步

定时同步按照固定周期扫描并复制增量数据，例如：

```text
每小时同步一次新增数据
每天执行一次完整校验
每周清理一次过期副本
```

定时同步实现简单，适合对实时性要求不高的业务，也可以作为事件同步失败后的兜底机制。

##### 版本就绪

对象已经出现在目标存储中，不代表整个数据集已经可以被训练任务使用。

一个数据集可能由成千上万个对象组成。如果训练任务在同步中途开始读取，可能得到不完整版本。

因此需要建立版本就绪机制：

```text
复制数据对象
      ↓
复制 Manifest
      ↓
校验对象数量、大小和哈希
      ↓
检查全部对象完成
      ↓
写入 READY 标记
      ↓
允许训练任务使用
```

训练任务只消费状态为 Ready 的数据集版本：

```text
datasets/sft/v3/data/*
datasets/sft/v3/manifest.json
datasets/sft/v3/_READY
```

这种设计将多云复制的一致性问题转化为版本级别的发布问题：

* 同步过程中，版本不可见；
* 完成校验后，版本整体可用；
* 旧版本继续保留；
* 同步失败不会影响正在使用的版本。

##### 冲突与删除策略

多云同步应尽量采用单写多读模式：

```text
主存储
→ 唯一写入源

目标存储
→ 只读副本
```

不建议允许多个云同时任意修改同一个数据集版本，否则需要处理覆盖冲突、删除冲突和版本分叉。

删除操作应与新增、修改分开处理。源端删除数据时，可以先将目标端对象标记为过期，等待保留期结束后再真正清理，避免同步错误造成不可逆的数据丢失。

#### 2.5.9 可观测性与故障恢复

生产环境中的存储系统不能只判断“是否可以挂载”，还需要持续观察其吞吐、延迟、缓存状态、数据库状态和对象存储回源情况。

JuiceFS 客户端会暴露 Prometheus 格式的监控指标，默认可以通过客户端的 Metrics Endpoint 获取。Prometheus 负责周期性采集和保存指标，Grafana 则负责展示趋势和构建告警面板。

```text
JuiceFS Client / Mount Pod
            ↓
       Metrics Endpoint
            ↓
        Prometheus
            ↓
          Grafana
            ↓
        告警与分析
```

##### JuiceFS 客户端指标

应重点关注：

* 文件读取和写入吞吐；
* IOPS；
* 读取和写入延迟；
* 元数据操作延迟；
* 对象存储请求延迟；
* 请求错误数量；
* 缓存命中情况；
* 缓存磁盘使用量；
* 当前挂载客户端数量。

##### 缓存指标

缓存层需要关注：

* 本地缓存命中率；
* 分布式缓存命中率；
* 对象存储回源流量；
* 缓存节点间读取流量；
* 缓存磁盘剩余容量；
* 缓存淘汰速度；
* 预热任务进度；
* 缓存节点失联数量；
* RDMA 与 TCP 数据路径状态。

##### 元数据服务指标

RDS 应监控：

* CPU、内存和磁盘使用率；
* 数据库连接数；
* QPS；
* 事务延迟；
* 慢查询；
* 主备复制延迟；
* 故障切换状态；
* 备份任务结果；
* 可恢复时间点。

##### Kubernetes 指标

需要关注：

* CSI Driver 状态；
* Mount Pod 重启次数；
* PVC 挂载失败；
* Pod 调度等待时间；
* Mount Pod 所在节点磁盘空间；
* 应用 Pod 与 Mount Pod 的生命周期；
* 预热任务失败次数。

##### 故障恢复

不同组件故障后的恢复方式不同：

| 故障           | 影响        | 恢复方式        |
| ------------ | --------- | ----------- |
| 本地缓存丢失       | 性能下降      | 从对象存储重新构建   |
| 单个缓存节点故障     | 部分请求回源    | 移出缓存组并重新缓存  |
| Mount Pod 故障 | 当前挂载短暂中断  | CSI 重新创建客户端 |
| 元数据主库故障      | 文件操作中断    | RDS 主备切换    |
| 对象存储不可用      | 缓存未命中读取失败 | 等待恢复或切换副本   |
| 跨云同步失败       | 新版本不可用    | 重试同步，保持旧版本  |
| 数据版本校验失败     | 阻止训练启动    | 修复副本并重新校验   |

恢复机制应遵循一个原则：

> 缓存故障可以通过回源恢复，元数据故障必须通过数据库高可用和备份恢复，远端数据故障则需要依赖对象存储可靠性或异地副本恢复。

#### 2.5.11 架构限制与适用边界

基于对象存储、JuiceFS、关系型元数据库和本地缓存构建的训练存储架构，并不是适用于所有 AI 训练场景的统一最优方案。

它更适合以下场景：

* 企业模型微调和后训练；
* 批量推理和离线评测；
* 多节点共享模型权重和训练数据；
* 数据一次写入、多次读取；
* 对象存储作为现有数据底座；
* 训练节点具有本地 SSD；
* 需要在容量、成本和性能之间取得平衡；
* 中小规模或中等规模 GPU 集群；
* 多云环境中的异步数据分发。

它的主要限制包括以下几个方面。

##### 元数据服务依赖

JuiceFS 的文件系统语义依赖元数据服务。即使对象存储仍然可用，元数据服务故障也可能导致文件系统无法正常访问。

因此，元数据数据库的性能、网络延迟和高可用能力会影响整个系统。

##### 缓存并非持久化存储

本地缓存和分布式缓存都可能被淘汰或丢失。缓存不能替代对象存储，也不能被视为模型和数据集的唯一副本。

##### 冷启动仍然存在

当缓存未命中时，数据仍然需要从对象存储读取。第一次加载大型模型或者新数据集时，性能仍然受到对象存储和网络带宽限制。

缓存预热能够将冷启动提前，但不能消除数据传输本身的成本。

##### 小文件和元数据压力

当数据集由海量小文件组成时，文件打开、目录遍历和元数据查询可能成为瓶颈。此时应优先考虑将小样本打包为 Parquet、Arrow、WebDataset 等适合批量读取的格式，而不是只依赖文件系统层优化。

##### 写密集型场景

这套架构更擅长读密集、重复读取的训练工作负载。对于高频随机写、频繁覆盖同一文件或大量节点同时写入 Checkpoint 的场景，需要单独评估写入吞吐和提交语义。

##### 跨云元数据延迟

对象数据可以复制到训练集群附近，但如果所有区域仍然访问同一个远端元数据服务，文件打开和目录操作仍然可能受到跨云网络延迟影响。JuiceFS 官方同样指出，对象数据复制主要改善数据访问性能，元数据性能仍然受网络距离影响。

##### 本地磁盘条件

如果训练节点没有本地 SSD，例如部分虚拟 GPU、Serverless 容器或者临时计算节点，本地缓存收益会明显下降。

此时可以使用独立缓存集群，但这也会增加额外的计算节点和运维成本。

##### 超大规模预训练

对于极大规模 GPU 集群、极高聚合带宽需求或者高频 Checkpoint 写入场景，可能需要进一步评估 Lustre、3FS、专用并行文件系统或高性能本地存储集群。

JuiceFS 架构在企业后训练和云原生数据共享方面具有较好的通用性，但不应未经测试直接推导到所有千卡、万卡训练集群。

##### 商业版能力和成本

分布式缓存、RDMA 和部分跨云能力可能依赖 JuiceFS 企业版或商业服务。采用这些能力时，需要将许可费用、供应商依赖和升级兼容性纳入总体成本评估。

---

#### 2.5.12 本章小结

本节以 JuiceFS 为核心，构建了一条面向企业 AI 训练场景的数据访问链路：

```text
对象存储
提供可靠、弹性的持久化能力
        ↓
元数据服务
维护文件系统命名空间和数据映射
        ↓
JuiceFS 客户端
提供统一的文件系统接口
        ↓
本地缓存与分布式缓存
降低远程访问和重复读取成本
        ↓
Kubernetes
将存储能力提供给训练任务
```

在此基础上，缓存预热可以降低训练任务冷启动时间，分布式缓存可以聚合多个训练节点的本地磁盘，RDMA 则可以进一步加速缓存节点之间的数据传输。

多云同步和版本就绪机制保证了训练数据能够被安全地复制到不同计算环境中，而 Prometheus、Grafana、数据库备份和故障恢复机制共同保证系统可以被持续观测和维护。

这套架构的核心并不是单纯使用 JuiceFS，而是将不同存储组件放在适合的位置：

* 对象存储负责长期可靠性；
* 元数据数据库负责文件系统语义；
* JuiceFS 负责统一访问接口；
* 缓存负责性能加速；
* Kubernetes 负责训练任务接入和调度；
* 数据同步负责跨云分发；
* 可观测系统负责发现和恢复故障。

只有明确每一层的职责和适用边界，才能在性能、可靠性、成本与运维复杂度之间形成稳定的生产架构。
