#### 5.1.1 优化原则

优化工作遵循以下顺序：

```text
正确性与可恢复性
        ↓
可观测与可定位
        ↓
数据布局与访问效率
        ↓
缓存与跨云分发
        ↓
专用网络和高级加速
```

每一项优化都必须说明：解决什么瓶颈、需要哪些前提、如何测量收益、失败时怎样回滚。没有监控证据的复杂度增加，不应进入生产架构。

#### 5.1.2 P0：版本与发布正确性

第一阶段先建立所有后续能力依赖的版本边界。

##### 不可变版本与 Manifest

需要完成：

* 数据集、模型和 Checkpoint 使用稳定版本号；
* 已发布版本不可覆盖；
* Manifest 记录对象、大小、校验值、Schema 和血缘；
* `_READY` 或控制平面状态只在全部校验通过后产生；
* 训练任务绑定具体版本，不在运行时解析 `latest`；
* 删除前检查训练、模型和审计引用。

完成标准是：任意训练任务都可以追踪到唯一数据版本，并能够在相同版本上重建输入。

##### 元数据备份与恢复

需要完成：

* 元数据数据库主备和自动故障切换；
* 自动备份、时间点恢复与异地备份；
* 定期在新实例执行恢复演练；
* 验证恢复后的文件系统可以挂载和读取；
* 记录 RPO、RTO 和最近一次演练结果。

只有备份任务成功而没有恢复演练，不能视为已经具备恢复能力。

#### 5.1.3 P0：数据控制平面

把散落在脚本和人工操作中的状态迁移收敛到统一控制平面：

* 建立 DatasetVersion、Replica、TransferTask 和 WarmupTask；
* 使用状态机管理发布、复制、校验和删除；
* 所有长任务支持幂等、租约、重试、取消和审计；
* 训练调度前检查版本和目标区域副本；
* 事件触发负责及时性，周期对账负责最终收敛；
* 凭证使用工作负载身份或短期授权。

完成标准是：人工不需要登录对象存储创建标记或修改任务状态，常见失败能够通过重试或明确的恢复流程处理。

#### 5.1.4 P0：可观测与容量基线

在继续优化前，先建立当前基线：

* JuiceFS 客户端读写吞吐、延迟和错误；
* 本地及分布式缓存命中率、淘汰和回源；
* 元数据数据库 QPS、连接、事务延迟和复制延迟；
* 对象存储 GET、PUT、List、限流、流量和费用；
* 节点磁盘、网络、CPU 和内存；
* DataLoader 等待、GPU 利用率和训练 Step 时间；
* 数据集发布到目标区域 `READY` 的端到端时间。

告警需要指向用户影响，例如训练无法挂载、版本长时间不能就绪、Checkpoint 超时或缓存穿透，而不只是某个组件 CPU 较高。

#### 5.1.5 P1：数据格式与分片

数据布局通常比增加存储组件更先产生收益。

##### 小文件合并

将海量独立样本转换为 Parquet、Arrow、WebDataset 或适合当前模态的分片格式，目标是：

* 降低对象请求与文件打开次数；
* 提高顺序读取和预取效率；
* 保持足够分片以供 Worker 并行；
* 保留样本级索引、校验和血缘；
* 支持问题样本定位和局部重建。

分片大小通过真实 DataLoader 测试确定，不能只依据行业经验固定。

##### Manifest 驱动读取

训练任务直接读取 Manifest 中的分片列表，避免启动时递归扫描 Bucket 或大型目录。Manifest 还可以承载样本数、行组统计和数据分布信息，帮助调度器均匀分配分片。

#### 5.1.6 P1：本地缓存治理

本地缓存优化包括：

* 将缓存盘与容器运行时、训练临时目录隔离；
* 设置容量上限和磁盘保留空间；
* 监控命中率、写放大、淘汰和磁盘寿命；
* 根据训练版本执行选择性预热；
* 任务取消时停止无效预热；
* 防止多个任务同时预热相同内容；
* 根据历史访问频率决定保留和淘汰优先级。

预热收益应以模型启动时间或训练等待改善衡量，而不是只报告预热完成字节数。

#### 5.1.7 P1：跨云复制与就绪

跨云训练稳定存在时，建设：

* 单一权威写入源；
* 版本级全量和增量复制；
* Manifest 数量、大小和哈希校验；
* `COPYING → VERIFYING → READY` 状态机；
* 事件触发与定时对账；
* 按链路限流和费用预算；
* 延迟删除与恢复窗口；
* 目标区域训练准入。

完成标准是：训练任务不会读取同步中的版本，主链路故障时旧的 `READY` 版本仍可使用。

#### 5.1.8 P1：Checkpoint 路径优化

Checkpoint 需要从读路径中独立评估：

* 将写入放到任务专属临时版本；
* 所有 Rank 完成后再提交恢复点；
* 将本地暂存与异步上传纳入故障语义；
* 控制并发上传，避免冲击训练读取；
* 按最近、里程碑和最终版本分层保留；
* 定期执行真实恢复测试；
* 监控保存时长、失败率和恢复成功率。

优化目标不是单纯提高 PUT 吞吐，而是降低训练阻塞并保证每个已提交版本确实可恢复。

#### 5.1.9 P2：分布式缓存

当指标证明多个节点反复下载相同数据，且本地缓存容量分散时，再引入分布式缓存。

实施重点包括：

* 缓存组节点的磁盘和网络尽量同构；
* 评估训练缓存一体与独立缓存集群；
* 观察远端缓存命中、本地命中和对象回源；
* 防止单块热点和缓存节点过载；
* 在节点退出时限制集中回源；
* 进行缓存组扩缩容和故障演练；
* 评估商业许可和供应商依赖。

若分布式缓存没有改善端到端训练时间或回源费用，应保留回退到本地缓存的能力。

#### 5.1.10 P2：RDMA 加速

只有在分布式缓存已经稳定运行，并证明 TCP 或主机 CPU 限制跨节点缓存吞吐后，才进入 RDMA 阶段。

需要验证：

* RDMA 驱动、网卡、交换机和网络隔离；
* RDMA 与 TCP 的功能一致性；
* 单节点和多节点吞吐、CPU 与尾延迟；
* RDMA 故障时的降级行为；
* 对真实模型加载和训练 Step 的改善；
* 升级、监控和排障流程；
* 商业版本成本。

如果瓶颈位于对象存储、元数据或缓存盘，先处理对应瓶颈。

#### 5.1.11 P2：元数据扩展

当监控确认元数据服务接近容量上限时，按顺序处理：

1. 减少不必要的 List、Stat 和小文件；
2. 优化客户端并发、连接和目录访问方式；
3. 提升数据库规格并缩短客户端网络距离；
4. 检查慢查询、锁、磁盘和主备复制；
5. 使用真实元数据工作负载比较其他引擎；
6. 评估按业务边界拆分文件系统，而不是破坏单卷事务。

更换元数据引擎必须包含迁移、回滚、双重校验和恢复演练。

#### 5.1.12 成本与生命周期优化

持续统计：

```text
总成本
= 对象容量 + API 请求 + 跨云流量
+ 缓存 SSD + 缓存节点 + 数据库
+ 商业许可 + 运维人力
```

可采用：

* 中间结果和临时 Checkpoint 自动过期；
* 正式数据集按引用和合规策略保留；
* 低频历史版本转入更低成本存储层；
* 避免长期保存没有训练引用的跨云副本；
* 按业务和数据集归集存储、请求和流量；
* 将每次训练的有效读取成本与 GPU 等待成本共同评估。

删除策略必须在版本引用、审计、法规和恢复窗口检查之后执行。

#### 5.1.13 安全与供应链

后续优化不能降低安全边界：

* 对象存储和数据库使用私网及加密连接；
* 凭证使用短期身份并定期轮换；
* 数据集按 Prefix、版本和租户最小授权；
* 正式数据集默认只读；
* 客户端、CSI Driver 和数据库升级经过兼容测试；
* 商业组件明确许可、支持和退出方案；
* 敏感数据访问、导出和删除均保留审计。

#### 5.1.14 路线图与退出条件

| 阶段 | 重点 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0 | 版本、控制平面、恢复、监控 | 数据可追踪、可恢复，瓶颈可观测 |
| P1 | 数据格式、本地缓存、多云、Checkpoint | 关键路径达到明确 SLO，成本可解释 |
| P2 | 分布式缓存、RDMA、元数据扩展 | 指标证明现有路径成为瓶颈且收益可验证 |

路线图应按季度或容量事件复核。节点数量、数据规模、文件分布、跨云比例或成本发生显著变化时，需要重新进行第 3 章的架构权衡和第 4 章的性能评估。
