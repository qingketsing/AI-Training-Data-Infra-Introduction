GPFS，即 IBM Storage Scale，是面向多节点共享访问的并行文件系统。它能够把多个存储节点、磁盘和网络资源组织成统一文件系统，并向计算节点提供高吞吐、低延迟和较完整的文件语义。

#### 3.4.1 并行文件系统能力

GPFS 将大文件分块并分布到多个磁盘，通过多个存储路径并行提供数据。对于大型训练分片、模型文件和高并发共享读取，它能够聚合磁盘、控制器和网络的能力。

```text
                    GPFS 文件系统
       ┌────────────────┼────────────────┐
       ▼                ▼                ▼
    存储节点 A        存储节点 B        存储节点 C
       │                │                │
    磁盘与阵列        磁盘与阵列        磁盘与阵列
```

这一设计适合：

* 多个节点并发读取同一文件系统；
* 大文件顺序或分片读取；
* 对共享写入和随机写要求较高的任务；
* 需要完整目录、权限、Rename 和锁语义的程序；
* 数据与计算主要位于稳定的高性能网络环境；
* 能够为文件系统配置专用存储节点和运维资源的团队。

IBM 官方将 Storage Scale 定位为多服务器并发访问的高性能共享文件系统，并通过数据条带化与 Token 管理支持并行读写。参考 [GPFS architecture](https://www.ibm.com/docs/en/storage-scale/6.0.0?topic=overview-gpfs-architecture) 和 [Improved system performance](https://www.ibm.com/docs/en/storage-scale/6.0.0?topic=scale-improved-system-performance)。

#### 3.4.2 一致性与并发访问

GPFS 使用细粒度 Token 和锁协调多个节点对文件、目录和文件系统资源的访问。它能够在并行环境中维持数据和元数据一致性，适合多个客户端共享读写同一命名空间。

但是，“具有分布式锁”不等于所有高并发模式都会自然获得更高性能。需要区分：

```text
多个节点读取不同文件或不同数据块
→ 容易利用并行存储能力

多个节点高频争用同一文件、目录或元数据热点
→ 可能产生 Token 迁移、锁等待和尾延迟
```

锁系统提供的是正确性基础。实际吞吐仍然取决于文件布局、访问冲突、磁盘、网络和 Token 管理负载。IBM 官方还提供专门的死锁检测与诊断机制，说明复杂锁依赖本身也是需要监控和运维的故障面。参考 [Managing deadlocks](https://www.ibm.com/docs/en/storage-scale/6.0.0?topic=troubleshooting-managing-deadlocks)。

#### 3.4.3 小文件与模型文件

GPFS 同时支持大量小文件和大型文件，但两类工作负载需要不同配置。

对于小文件，需要关注：

* inode 数量与文件系统格式；
* 元数据磁盘和系统存储池；
* `maxFilesToCache` 和 Stat Cache；
* 目录热点和高频创建、删除；
* 客户端内存与 Pagepool；
* 元数据节点和网络延迟。

对于聚合数据和模型文件，需要关注：

* 文件系统块大小；
* 数据条带和存储池布局；
* NSD Server 与客户端网络；
* 顺序读取和预取；
* 多节点同时加载模型时的聚合带宽；
* Checkpoint 并发写入产生的突发负载。

GPFS 使用独立 Pagepool 缓存用户数据和文件系统元数据。Pagepool、文件缓存和操作系统内存之间需要统一规划，错误配置可能影响训练任务可用内存。参考 [Cache usage](https://www.ibm.com/docs/en/storage-scale/6.0.0?topic=considerations-cache-usage)。

#### 3.4.4 多云与 Kubernetes

GPFS 并非完全不具备多站点和 Kubernetes 能力。Storage Scale 提供：

* 多集群远程文件系统访问；
* AFM Cache 与 Home 关系；
* 跨站点数据缓存和复制；
* Kubernetes CSI Driver 与容器化部署组件；
* 远程集群和缓存网关的管理能力。

AFM 可以让缓存集群从远端 Home 按需读取并缓存数据，也可以连接云对象存储。参考 [Active File Management](https://www.ibm.com/docs/en/storage-scale/6.0.0?topic=reference-active-file-management-afm) 和 [Enabling AFM caching](https://www.ibm.com/docs/en/storage-scale/6.0.0?topic=cloudkit-enabling-afm-caching)。

这些能力能够解决多站点问题，但会继续引入 Storage Scale 集群、AFM Gateway、Fileset、远程协议、版本兼容和故障恢复流程。对于已经以对象存储作为权威数据源的环境，这条路线的系统边界和实施成本通常比直接采用对象存储原生后端更重。

#### 3.4.5 建设与运维成本

GPFS 的完整成本不只包含 License：

```text
GPFS 总成本
= 软件 License
+ 存储节点与客户端授权
+ 磁盘、阵列和冗余容量
+ 高速网络与交换设备
+ 部署和迁移实施
+ 原厂及集成商支持
+ 升级、扩容和故障演练
+ 内部存储运维人力
```

实际运行中需要同时管理硬件、网络、磁盘、文件系统、集群仲裁、版本兼容和性能参数。在故障排查、版本升级和性能调优时，原厂支持、实施经验和响应效率都会直接影响恢复时间。

因此，选型时不能只比较软件能力。至少需要取得：

* 目标容量和节点数下的完整报价；
* 硬件与网络参考架构；
* Kubernetes、操作系统和 Storage Scale 兼容矩阵；
* 原厂及集成商支持范围与 SLA；
* 扩容、升级和跨站点部署方案；
* 团队能够独立处理的问题边界。

#### 3.4.6 当前场景下的判断

GPFS 更适合以下条件：

* 预算充足，并愿意建设专用高性能存储底座；
* 对低延迟、强文件语义、共享写入和随机写要求较高；
* 计算与存储节点相对稳定；
* 主要数据位于 GPFS 管理的存储池；
* 团队或合作方具备长期 Storage Scale 运维和调优能力。

当前场景已经存在对象存储，需要跨云使用数据，并希望通过 Kubernetes 快速接入不同训练环境。采用 GPFS 仍然可行，但需要额外建设新的权威存储或复杂的 AFM 数据路径，并承担较高的软硬件和支持成本。

因此，本章不把 GPFS 判断为能力不足，而是认为它在当前约束下存在系统偏重、迁移和运维成本较高的问题。如果未来场景转向固定的超大规模高性能计算集群，并且共享写入、低延迟和随机写成为首要矛盾，GPFS 应重新进入重点评估范围。
