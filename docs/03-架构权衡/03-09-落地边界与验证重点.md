架构选型只能确定建设方向，不能代替生产验证。JuiceFS 的综合适配度更高，并不意味着对象存储、元数据、缓存和网络能够在任意配置下满足大规模训练。自建 NAS、GPFS、CephFS 和 Alluxio 作为候选方案时，也应使用相同数据集、并发模型和指标口径进行对照。

#### 3.9.1 小文件验证

小文件测试需要使用真实文件数量、目录深度和并发模式，至少验证：

* 文件创建、Open、Stat、List 和删除吞吐；
* 元数据数据库 QPS、连接数和事务延迟；
* 目录热点和大量客户端同时挂载；
* 冷读取和热缓存读取差异；
* 单文件保存与聚合分片的成本和性能；
* Manifest 读取是否能够替代递归目录扫描；
* 元数据主备切换期间的任务影响。

如果小文件压力主要来自可聚合训练样本，应先调整数据格式，而不是只扩大元数据数据库。

#### 3.9.2 聚合数据与模型加载验证

需要分别测试：

* 单节点读取聚合训练分片；
* 多 Worker 读取不同分片；
* 多节点同时加载同一模型；
* 对象存储直接读取；
* JuiceFS 冷缓存；
* 本地热缓存；
* 分布式缓存 TCP；
* 目标云副本和跨云回源；
* 预热前后的任务启动时间。

最终指标应包括模型加载时间、聚合吞吐、P95/P99 延迟、对象存储回源、缓存命中和 GPU 数据等待，而不只是客户端峰值带宽。

#### 3.9.3 Checkpoint 验证

Checkpoint 必须作为独立写路径测试：

* 单次 Checkpoint 大小和文件数量；
* 多 Rank 并发写入；
* 上传到对象存储的持续和峰值带宽；
* 保存过程对训练 Step 的阻塞；
* 临时版本到正式恢复点的提交；
* 部分 Rank 失败后的半成品清理；
* Mount Pod 或客户端重启后的恢复；
* 从已提交 Checkpoint 执行真实恢复；
* Checkpoint 保留、归档和删除策略。

只有能够被真实恢复的版本，才能被标记为有效 Checkpoint。

#### 3.9.4 多云验证

多云场景至少需要验证：

* 历史数据第一次全量复制；
* 新版本增量复制；
* Manifest 数量、大小和哈希校验；
* 目标区域从 `COPYING` 到 `READY` 的延迟；
* 同步中断、重试和幂等；
* 对象数据完成但元数据延迟较高的情况；
* 目标云缺少数据块时的回源；
* 模型版本在多个云同时分发；
* 主对象存储不可用时的切换路径；
* 跨云流量、请求和副本容量成本。

训练任务只能使用目标区域已经完成校验的版本，不能通过对象或目录已经出现来判断整个版本可用。

#### 3.9.5 Kubernetes 与弹性验证

需要覆盖：

* CSI Driver 和 Mount Pod 重启；
* 训练 Pod 重建和跨节点调度；
* 节点扩容时的自动挂载；
* 节点缩容时的缓存和挂载处理；
* 缓存盘空间不足；
* 多个训练任务争用同一缓存盘；
* 固定缓存集群成员加入和退出；
* 短期凭证更新与权限隔离；
* 正式数据集只读和 Checkpoint 目录可写；
* CSI、JuiceFS 客户端和 Kubernetes 升级兼容性。

#### 3.9.6 故障恢复验证

| 故障 | 预期行为 |
| --- | --- |
| 本地缓存丢失 | 任务能够回源，性能下降但数据不丢失 |
| 单个缓存节点故障 | 哈希环或缓存组降级，不造成正式数据损坏 |
| 对象存储短暂限流 | 客户端受控重试，不形成无限请求放大 |
| 元数据主库故障 | 主备切换后恢复文件访问 |
| Mount Pod 故障 | CSI 自动重建挂载客户端 |
| 跨云同步失败 | 新版本保持不可用，旧 `READY` 版本继续服务 |
| Manifest 校验失败 | 阻止版本进入训练准入流程 |
| Checkpoint 部分写入失败 | 不发布为可恢复版本 |
| NAS 控制节点或链路故障 | 客户端按高可用设计恢复，已提交数据保持完整 |
| CephFS MDS 或 OSD 故障 | 元数据服务接管或数据降级恢复，前台影响可量化 |

故障验证需要记录恢复时间、训练错误、回源流量和尾延迟，而不只是判断服务最终是否恢复。

#### 3.9.7 成本验证

最终方案需要持续统计：

```text
总成本
= 对象存储容量
+ GET、PUT、List 和 Head 请求
+ 跨云及跨地域流量
+ 元数据数据库
+ 缓存 SSD 和缓存节点
+ JuiceFS 企业版或支持服务
+ Kubernetes 与监控资源
+ 运维和故障处理人力
```

应进一步计算每个数据集版本、每次模型分发和每个训练任务的有效读取成本，避免用总账掩盖低命中缓存、重复副本和无效预热。

对照方案还应计入 NAS 或 CephFS 的服务器、磁盘、存储网络、备件、机房资源和恢复期间的性能损失，不能只比较软件 License。

#### 3.9.8 决策边界

当前选择 JuiceFS 的前提是：

* 对象存储继续作为主要持久化底座；
* 工作负载以大规模数据生产、读取和版本分发为主；
* 小文件可以通过元数据扩展和部分数据聚合治理；
* Checkpoint 写入能够在对象存储路径上达到业务目标；
* Kubernetes 与多云是长期需求；
* 团队能够运维元数据、缓存和同步控制平面。

任何一个关键前提被实测否定，都需要重新打开第 3.8 节的选型决策。
