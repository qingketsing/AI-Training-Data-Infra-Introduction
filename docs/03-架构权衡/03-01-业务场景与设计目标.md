第三章不再从单个存储组件出发，而是基于当前业务场景，对不同技术路线进行整体权衡。选型目标不是寻找所有单项指标都最强的系统，而是在数据生产、训练读取、多云分发、迁移成本和运维能力之间，选择综合适配度最高的方案。

#### 3.1.1 业务范围

当前数据基础设施需要覆盖大规模数据生产与模型训练的完整链路：

```text
外部与内部数据源
        ↓
数据接入、清洗、标注与聚合
        ↓
候选数据集与正式版本发布
        ↓
模型训练、评测与 Checkpoint
        ↓
模型发布与多云分发
```

这意味着存储系统不能只优化训练读取，也不能只作为离线归档。数据生产任务、训练任务和模型分发任务会共享同一套数据底座，但三者具有不同的访问模式和一致性要求。

#### 3.1.2 数据类型

系统需要同时处理小文件、聚合训练数据和大型模型文件。

| 数据类型 | 典型内容 | 主要访问模式 | 核心要求 |
| --- | --- | --- | --- |
| 原始数据 | 日志、网页、图片、音频、业务记录 | 持续写入、批量扫描 | 容量、可靠性、成本和合规 |
| 小文件 | 独立样本、元数据、索引和配置 | 高频 Open、Stat 和随机读取 | 元数据性能、请求延迟和目录能力 |
| 聚合数据 | Parquet、Arrow、WebDataset 等训练分片 | 多 Worker 顺序或范围读取 | 聚合吞吐、分片调度和预读效率 |
| 模型权重 | Safetensors、Tokenizer 和配置 | 多节点重复读取 | 冷启动、缓存复用和版本分发 |
| Checkpoint | 训练状态、优化器和模型分片 | 周期性并发写入 | 写入吞吐、提交一致性和恢复能力 |
| 中间产物 | 清洗结果、标注结果和临时聚合文件 | 读写混合、生命周期较短 | 自动清理、成本和可重建性 |

不同数据类型不能使用完全相同的优化策略。小文件更容易受到元数据和请求延迟影响，聚合数据更关注顺序吞吐，模型权重适合预热和跨节点复用，而 Checkpoint 需要独立设计写入及提交路径。

#### 3.1.3 多云协同

训练资源可能来自不同云厂商或不同地域。数据基础设施需要支持：

* 将正式数据集复制到计算集群附近；
* 在不同云中保持统一的数据集和模型版本标识；
* 避免训练任务直接读取同步中的半成品版本；
* 控制跨云带宽、延迟和流量费用；
* 支持模型权重和热门数据集的按需分发；
* 在目标云故障或副本不可用时保留回源与回滚路径；
* 将对象数据复制和文件系统元数据问题分别处理。

多云能力不只是“能够连接多个 Bucket”。完整方案还需要版本状态、Manifest、同步校验、目标区域就绪和训练准入机制。

#### 3.1.4 计算与调度环境

训练和数据处理任务主要运行在 Kubernetes 或由 Kubernetes 管理的计算环境中，因此存储方案需要考虑：

* CSI、FUSE 或用户态客户端的接入方式；
* Pod 和挂载客户端的生命周期；
* GPU 节点扩缩容和本地 SSD 条件；
* 缓存节点与计算节点是否共用资源；
* 多租户目录与权限隔离；
* 节点重启后的挂载恢复和缓存恢复；
* 客户端、CSI Driver 与 Kubernetes 版本兼容性。

一个在固定裸金属集群中表现良好的缓存方案，不一定适合频繁扩缩容的弹性 Pod。计算生命周期和缓存生命周期需要分别设计。

#### 3.1.5 选型目标

结合当前业务范围，方案需要在以下目标之间取得平衡：

1. **全流程覆盖**：同时服务数据生产、训练读取、Checkpoint 和模型分发；
2. **对象存储复用**：尽量复用已经存在的 OSS、S3、TOS 或其他对象数据；
3. **混合文件适配**：能够处理小文件、聚合分片和大型模型文件；
4. **多节点共享**：向不同训练节点提供统一文件路径和版本；
5. **多云分发**：支持数据与模型按版本复制到目标计算区域；
6. **Kubernetes 接入**：具备稳定的容器挂载、恢复和可观测能力；
7. **性能可扩展**：允许通过本地缓存、分布式缓存和数据布局逐步优化；
8. **可靠性**：权威数据、元数据和缓存副本的职责边界清晰；
9. **迁移成本可控**：不要求一次性重新组织所有已有数据；
10. **可运维性**：团队能够独立完成日常监控、升级和常见故障处理；
11. **成本可解释**：容量、请求、流量、硬件、License 和人力成本可以统一评估。

#### 3.1.6 评估维度

本章使用统一维度比较自建 NAS、GPFS、CephFS、Alluxio 和 JuiceFS：

| 维度 | 评估问题 |
| --- | --- |
| 系统角色 | 它是权威存储、完整文件系统，还是缓存与数据访问层？ |
| 数据路径 | 数据写入、读取、缓存未命中和故障恢复分别经过哪些组件？ |
| 文件语义 | 是否满足数据生产和训练程序需要的文件操作？ |
| 小文件能力 | 元数据、目录遍历和大量文件打开如何扩展？ |
| 大文件能力 | 模型和聚合分片能否获得稳定聚合吞吐？ |
| 写入能力 | Checkpoint、随机更新和并发写入的边界是什么？ |
| 多云能力 | 数据、元数据、版本和目标区域就绪如何实现？ |
| Kubernetes | 如何挂载、恢复、扩缩容和隔离？ |
| 运维复杂度 | 需要维护哪些硬件、网络、数据库和控制组件？ |
| 迁移成本 | 是否能够复用已有对象存储和路径？ |
| 商业成本 | License、硬件、支持服务和实施成本是多少？ |
| 团队能力 | 现有经验能否覆盖部署、调优和故障处理？ |

后续比较只在这些业务约束内成立。如果未来工作负载转向极大规模预训练、高频随机写或完全本地化的高性能计算集群，需要重新进行选型，而不能直接沿用本章结论。
