自建 NAS、GPFS、CephFS、Alluxio 和 JuiceFS 都能够出现在 AI 数据访问链路中，但它们解决的问题并不相同。如果不先区分系统角色，只比较吞吐、缓存或接口数量，容易得到错误结论。

#### 3.2.1 自建 NAS 的系统角色

自建 NAS 通常以通用服务器、本地磁盘阵列和 NFS 构成集中式共享存储。它的优势是简单、成本可控，适合作为中小规模共享目录、数据中转和性能基线；主要边界是存储头、网络和盘位的纵向扩展能力。

#### 3.2.2 GPFS 的系统角色

GPFS，即当前的 IBM Storage Scale，是一套并行文件系统。它通过存储节点、磁盘、网络、文件系统客户端和集群控制组件，共同提供统一的共享文件系统，强调完整文件语义、并行访问、共享写入和底层存储吞吐。

GPFS 可以通过 AFM、远程集群挂载等能力连接其他站点或存储，但这些能力仍然建立在完整的 Storage Scale 集群、网关和文件集管理体系上。

#### 3.2.3 CephFS 的系统角色

CephFS 是建立在 RADOS 之上的开源分布式文件系统。MDS 处理文件元数据，客户端直接访问 OSD 中的数据，可以通过增加存储节点、磁盘和 MDS 扩展能力。它适合自有硬件和单地域共享文件访问，但需要建设完整的 Ceph 数据面。

#### 3.2.4 Alluxio 的系统角色

Alluxio 位于计算和已有存储系统之间。它把 S3、HDFS、Ceph、MinIO、NAS 等不同 Under File Storage 挂载到统一命名空间，并利用 Worker 的内存、SSD 或 HDD 形成分布式缓存。

权威数据通常仍保存在底层 UFS 中。因此，Alluxio 更接近数据访问与缓存层。将它用于完整数据生产和写入链路时，需要确认具体版本、接口、WriteType、持久化方式和文件操作边界。

#### 3.2.5 JuiceFS 的系统角色

JuiceFS 将文件内容保存到对象存储，并通过独立元数据服务维护目录、权限、文件属性和数据块映射。客户端向应用提供统一文件系统接口，同时使用本地或分布式缓存降低对象存储访问成本。

JuiceFS 既不是传统共享磁盘并行文件系统，也不只是透明缓存。它以对象存储作为数据持久化底座，并在其上提供完整、可扩展的文件系统命名空间，与当前已有对象存储、多云计算和 Kubernetes 训练环境更接近。

#### 3.2.6 五种路线的根本差异

| 方案 | 核心角色 | 权威数据位置 | 主要适用方向 |
| --- | --- | --- | --- |
| 自建 NAS | 集中式共享文件存储 | NAS 本地磁盘或阵列 | 中小规模共享、数据中转与基线 |
| GPFS | 商业并行文件系统 | GPFS 管理的磁盘与存储池 | 高性能计算、共享写入和完整文件语义 |
| CephFS | 开源分布式文件系统 | RADOS 集群 | 自有硬件上的横向扩展文件存储 |
| Alluxio | 统一数据访问与缓存层 | 底层 UFS | 异构存储统一访问与缓存加速 |
| JuiceFS | 对象存储上的分布式文件系统 | 对象存储与元数据服务 | 对象复用、文件访问与多云分发 |

因此，本章的选型问题不是简单判断哪一个系统“更快”，而是判断哪一种系统角色更符合当前架构：

```text
简单、低成本的中小规模共享存储？              → 自建 NAS
成熟的商业并行文件系统和高性能共享写入？      → GPFS
自有硬件上的开源横向扩展文件系统？            → CephFS
为已有多套存储增加统一访问和缓存？            → Alluxio
以对象存储为权威底座并提供文件系统接口？      → JuiceFS
```

#### 3.2.7 比较原则

后续评估遵循以下原则：

* 不使用单项峰值性能代替端到端训练效果；
* 不把某个产品的可选扩展能力视为默认部署能力；
* 明确区分开源版、企业版和依赖商业服务的功能；
* 将数据正确性、故障恢复和运维复杂度与性能同时比较；
* 将已有对象存储和迁移成本纳入总体成本；
* 将团队已有经验视为实际约束，但不替代性能与故障验证；
* 对可能改变结论的条件明确记录，而不是给出永久性的绝对判断。

五种方案的具体优缺点将在后续分节中展开。
