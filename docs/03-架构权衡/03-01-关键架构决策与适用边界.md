#### 3.1.1 先描述工作负载

架构选型之前，应先形成可量化的工作负载画像：

| 维度 | 需要回答的问题 |
| --- | --- |
| 容量 | 当前数据量、增长速度、保留周期和版本数量是多少？ |
| 文件 | 文件数量、大小分布和数据格式是什么？ |
| 读取 | 顺序还是随机、一次还是重复、多节点是否读取相同内容？ |
| 写入 | 数据集发布和 Checkpoint 的大小、频率与并发是多少？ |
| 计算 | 节点数、Worker 数、生命周期和本地 SSD 条件是什么？ |
| 网络 | 计算与数据是否同地域，聚合带宽与跨云费用是多少？ |
| 恢复 | 允许的 RPO、RTO 和训练中断时间是多少？ |
| 合规 | 数据地域、加密、审计和租户隔离要求是什么？ |
| 团队 | 是否具备存储、数据库、网络和 Kubernetes 运维能力？ |

没有工作负载数据时，选型只能得到假设。所有关键决策都应附带适用条件，并在条件变化后重新评估。

#### 3.1.2 直接访问对象存储还是引入文件系统

直接使用 S3 API 或数据框架的对象存储连接器，链路简单且没有额外元数据服务，适合：

* 应用原生支持对象存储；
* 数据主要按不可变分片顺序读取；
* 不依赖 POSIX 路径、Rename 和目录语义；
* 团队希望减少基础组件数量；
* 数据处理任务能够自行处理重试、提交和版本。

引入 JuiceFS 等文件系统层更适合：

* 现有训练代码依赖普通文件路径；
* 多个框架需要共享统一命名空间；
* 模型、数据集和 Checkpoint 需要以目录方式组织；
* 需要透明接入本地或分布式缓存；
* Kubernetes 希望通过 CSI 统一挂载。

| 维度 | 直接对象访问 | 文件系统抽象 |
| --- | --- | --- |
| 链路复杂度 | 低 | 增加客户端和元数据服务 |
| 应用兼容性 | 需要应用支持对象 API | 大部分文件路径程序可直接使用 |
| 目录与 Rename | 需要业务模拟 | 由文件系统提供相应语义 |
| 元数据依赖 | 对象存储自身 | 独立元数据引擎 |
| 缓存接入 | 应用或框架自行实现 | 可以由文件系统统一实现 |
| 故障面 | 较小 | 需要同时运维客户端和元数据服务 |

不应仅因为“训练都需要高性能”就默认引入文件系统。如果应用已经能够高效读取对象分片，额外抽象可能没有足够收益。

#### 3.1.3 托管对象存储还是自建对象存储

托管对象存储将硬件、扩容和大部分故障处理交给云厂商，能够缩短上线时间；自建对象存储则提高数据位置和硬件配置的控制能力。

决策时应比较完整 TCO：

```text
托管 TCO = 容量 + 请求 + 读取 + 跨地域流量 + 支持费用

自建 TCO = 服务器 + 磁盘 + 网络 + 机房
         + 冗余容量 + 备件 + 运维人力 + 故障风险
```

以下情况通常倾向托管服务：

* 计算主要位于同一公有云；
* 容量增长不确定；
* 团队缺少专职存储运维；
* 需要快速建立跨可用区可靠性。

以下情况可以评估自建方案：

* 数据必须位于本地或私有环境；
* 已有机房、高速网络和成熟存储团队；
* 数据量和访问量长期稳定且足以摊薄建设成本；
* 需要控制磁盘、冗余、网络和升级节奏。

自建不等于天然便宜，托管也不等于无需容量和费用治理。

#### 3.1.4 元数据引擎选择

元数据引擎影响文件打开、目录遍历、小文件访问和系统恢复。选型需要同时看性能、事务、容量、高可用和团队经验。

| 类型 | 优点 | 风险与成本 | 更适合的场景 |
| --- | --- | --- | --- |
| Redis 类 | 低延迟、元数据操作性能高 | 内存成本、持久化与容量规划更严格 | 高元数据 QPS、团队具备 Redis 运维能力 |
| MySQL/PostgreSQL 类 | 事务成熟、托管服务与备份体系完善 | 纯元数据性能可能低于内存数据库 | 企业后训练、可靠性和可维护性优先 |
| 分布式事务 KV | 可扩展和高可用能力强 | 部署、调优和排障更复杂 | 元数据规模很大且已有相应基础设施 |

一个文件系统的元数据需要保持事务一致性，不能为了“水平扩展”就随意按表或目录拆到彼此独立的数据库中。应先通过真实文件数量、元数据 QPS 和延迟测试确认单一逻辑实例是否成为瓶颈。

#### 3.1.5 不使用缓存、本地缓存还是分布式缓存

缓存的收益取决于数据复用，而不是数据总量。

```text
重复读取次数低 + 对象存储同地域且带宽充足
→ 可以先不建设缓存

节点固定 + 本地 SSD 充足
→ 优先使用本地缓存

多节点重复读取相同内容 + 高速内网
→ 评估分布式缓存

计算节点短生命周期或没有本地盘
→ 评估独立缓存集群
```

| 模式 | 优点 | 代价 |
| --- | --- | --- |
| 无缓存 | 组件最少、数据一致性简单 | 每次读取都访问远端 |
| 本地缓存 | 路径短、热读性能高 | 容量分散、节点间重复保存 |
| 分布式缓存 | 聚合容量、跨节点共享、减少集中回源 | 节点发现、网络访问和故障处理更复杂 |
| 独立缓存集群 | 生命周期稳定、不与训练 Pod 绑定 | 需要额外节点和运维预算 |

预热也有成本。若一个版本只读取一次，预热只是把同一份远端传输提前执行；若任务最终未启动，还会浪费网络和缓存容量。

#### 3.1.6 TCP 还是 RDMA

RDMA 应当是性能分析后的优化项，而不是架构起点。引入前需要证明：

* 数据主要从其他缓存节点读取；
* 节点间 TCP 或 CPU 已成为瓶颈；
* 缓存盘和对象存储不是当前瓶颈；
* 集群具有稳定的 RDMA 网络、驱动和运维能力；
* 收益能够覆盖商业许可、网络和排障成本。

如果训练大部分读取命中本地 SSD，跨节点数据路径占比很低，RDMA 对整体任务时间的影响也会很低。优化必须观察端到端训练时间，而不能只比较网络微基准。

#### 3.1.7 单云访问还是多云复制

单云同地域的数据访问路径最简单，适合计算资源和业务长期稳定的场景。多云复制能够把数据放到算力附近并降低长期跨云读取，但会引入复制延迟、版本状态、额外容量和出口流量。

以下条件满足时，多云复制更有价值：

* 跨云训练是持续需求而非偶发任务；
* 同一版本会在目标云被重复读取；
* 目标云需要明确的可用副本和容灾能力；
* 跨云流量或延迟明显影响训练；
* 团队能够维护 Manifest、状态机、校验和删除策略。

对于偶发的小规模任务，按任务临时复制指定版本可能比长期维护完整副本更经济。

#### 3.1.8 一套文件系统还是按区域拆分

跨区域共享同一元数据服务能够保持统一命名空间，但远端客户端的元数据操作会受到网络往返延迟影响。按区域建立独立文件系统能够缩短元数据路径，却需要同步对象数据和命名空间状态。

决策可以参考：

* 大文件顺序读取、目录操作较少时，共享元数据服务可能仍然可接受；
* 海量小文件、频繁 `stat` 或目录遍历时，跨区域元数据延迟更敏感；
* 需要区域独立故障域时，应评估镜像或独立文件系统；
* 不论采用哪种方式，业务层数据集版本都应保持统一标识。

#### 3.1.9 读路径与写路径分离

训练数据、模型权重和 Checkpoint 不应使用完全相同的策略：

| 数据类型 | 主要模式 | 推荐重点 |
| --- | --- | --- |
| 已发布数据集 | 一次写入、多次读取 | 不可变版本、只读、缓存和分片 |
| 模型权重 | 大文件、多节点重复加载 | 预热、分布式缓存和版本校验 |
| Checkpoint | 周期性并发写入 | 临时版本、提交协议、写入带宽和保留策略 |
| 中间处理结果 | 可重建、生命周期短 | 低成本存储和自动清理 |
| 原始业务数据 | 高合规要求 | 权限隔离、加密和审计 |

对读路径有效的激进缓存策略，不一定能改善 Checkpoint 的突发写入；对正式数据集有效的不可变策略，也不适合尚在生成的临时结果。

#### 3.1.10 可靠性、性能、成本与复杂度

架构评审需要同时观察四个方向：

```text
可靠性：数据能否恢复，故障域是否清晰？
性能：训练是否等待，尾延迟是否可控？
成本：容量、请求、流量、许可和人力是多少？
复杂度：团队能否部署、监控、升级和排障？
```

任何优化都至少会改变其中两项。例如，增加跨云副本可以改善目标区域性能和容灾，但会增加容量、同步流量和控制平面复杂度。决策记录应明确这项交换，而不是只描述收益。

#### 3.1.11 架构决策记录

每个重要决策建议保存一份 ADR，包含：

* 背景和工作负载数据；
* 决策问题；
* 候选方案；
* 可靠性、性能、成本与复杂度比较；
* 最终方案及理由；
* 适用条件和明确不覆盖的场景；
* 需要验证的假设；
* 监控指标和回滚条件；
* 复核日期。

当 GPU 节点数量、数据格式、云厂商、访问频率或成本模型发生显著变化时，应重新打开相关 ADR，而不是让过去的假设永久固化为架构。

#### 3.1.12 推荐的渐进式路径

对于企业微调和后训练，可以采用逐步增强的建设顺序：

1. 使用同地域对象存储保存不可变数据版本；
2. 先优化数据格式和分片，建立 Manifest；
3. 应用确实依赖文件路径时再引入文件系统层；
4. 建立元数据高可用、备份、监控和恢复演练；
5. 通过指标确认重复远程读取后启用本地缓存；
6. 多节点重复读取且高速内网可用时评估分布式缓存；
7. 只有 TCP 或 CPU 成为瓶颈时再评估 RDMA；
8. 跨云训练成为稳定需求后建设版本级复制与控制平面。

这种顺序允许每一层复杂度都由明确问题驱动，并为后续性能评估提供可比较的基线。
