#### 4.1.1 评估原则

一次可信的性能评估应遵循以下原则：

* **面向业务结果**：以训练启动时间、Step 时间、GPU 等待和 Checkpoint 时间作为最终判断；
* **固定变量**：比较缓存或网络模式时，数据、并发、节点和读取顺序保持一致；
* **冷热分离**：明确区分冷缓存、本地热缓存和分布式缓存命中；
* **端到端观测**：同时采集客户端、数据库、对象存储、缓存、网络、CPU 和 GPU 指标；
* **报告尾延迟**：平均值不能代表训练集群中最慢 Worker；
* **保存原始证据**：环境、命令、日志、查询和版本必须可以复现；
* **不外推环境**：厂商或其他集群的基准只能用于参考，不能直接作为本系统结果。

#### 4.1.2 定义性能目标

性能目标应从训练任务反推，而不是先设定存储峰值。

##### 训练读取

```text
单 Worker 消费带宽
= 每秒消费样本数 × 平均样本读取字节数

集群有效读取需求
= 单 Worker 消费带宽 × 并行 Worker 数
```

若数据存在解压、列裁剪或 Range Read，训练消费字节与底层网络字节可能不同，必须分别测量。

##### 模型加载

```text
允许的最低模型加载吞吐
= 模型总字节数 / 任务启动预算
```

多节点同时加载模型时，需要同时满足单节点吞吐和集群聚合吞吐，不能用一个节点的热缓存结果代表整个集群。

##### Checkpoint

```text
允许的最低 Checkpoint 吞吐
= Checkpoint 总字节数 / 保存时间预算
```

如果保存过程阻塞训练，还要把保存频率纳入有效训练效率：

```text
Checkpoint 阻塞占比
= 单次保存时间 / 保存间隔
```

#### 4.1.3 固化测试环境

每份报告应记录：

* 测试时间和测试区域；
* JuiceFS、CSI Driver、操作系统和内核版本；
* 挂载参数、缓存参数与缓存组配置；
* 元数据引擎类型、版本、规格和高可用方式；
* 对象存储类型、Endpoint、Bucket 和访问网络；
* 客户端 CPU、内存、SSD 型号、容量和文件系统；
* 网卡速率、TCP 或 RDMA 模式及网络拓扑；
* Kubernetes 节点、Pod 资源限制和调度位置；
* 数据集格式、总大小、对象数量和大小分布；
* Worker 数量、并发度、Batch 和预取参数。

只要其中一个关键变量发生变化，就应创建新的结果记录，不能覆盖旧报告。

#### 4.1.4 分层测试

性能测试应从底向上进行，这样才能定位瓶颈。

##### 第一层：本地资源

验证缓存盘顺序读写、随机读写、可用容量、磁盘队列和 CPU 能力。这里的结果是热缓存性能的物理上界之一。

##### 第二层：网络

分别验证：

* 客户端到对象存储的吞吐与延迟；
* 客户端到元数据数据库的往返延迟；
* 缓存节点之间的 TCP 吞吐；
* 使用 RDMA 时的 RDMA 吞吐、错误和降级路径；
* 多节点同时运行时的交换机或出口聚合带宽。

单连接测速不能代替多节点聚合测试。

##### 第三层：对象存储

使用对象存储基准或 `juicefs objbench` 一类工具检查：

* PUT、GET、HEAD 和 List；
* 大对象顺序读取；
* Range Read；
* 小对象并发；
* 首字节延迟；
* 限流、重试和错误率；
* 内网与跨云 Endpoint 差异。

##### 第四层：元数据

使用 `stat`、创建、打开、目录遍历和小文件访问评估元数据路径，同时观察数据库 QPS、事务延迟、连接数、CPU、磁盘和主备复制延迟。

##### 第五层：文件系统与缓存

比较以下数据路径：

1. 对象存储直接访问；
2. JuiceFS 冷缓存；
3. JuiceFS 本地热缓存；
4. 分布式缓存 TCP；
5. 分布式缓存 RDMA；
6. 缓存节点故障后的回源路径。

##### 第六层：真实应用

运行真实模型加载、DataLoader、训练 Step 和 Checkpoint。应用测试必须使用生产数据格式和相同的解析、打乱、解压、Batch、预取逻辑。

#### 4.1.5 工作负载矩阵

| 工作负载 | 主要观察指标 | 主要风险 |
| --- | --- | --- |
| 单节点加载大模型 | 加载时间、吞吐、CPU、缓存命中 | 冷启动过长 |
| 多节点加载同一模型 | 聚合吞吐、回源流量、热点节点 | 惊群回源 |
| 大文件顺序训练读取 | 有效吞吐、GPU 等待 | 网络或磁盘饱和 |
| 小文件并发读取 | Open/Stat 延迟、数据库 QPS | 元数据瓶颈 |
| 随机范围读取 | P95/P99、读放大 | 首字节延迟和缓存离散 |
| 缓存预热 | 完成时间、预热字节、任务收益 | 预热挤占训练带宽 |
| Checkpoint 写入 | 保存时间、并发 PUT、提交成功率 | 写入突发和半成品 |
| 缓存节点故障 | 降级时间、回源流量、任务错误 | 对象存储被击穿 |
| 元数据主备切换 | 文件操作中断和恢复时间 | 挂载或训练失败 |
| 跨云副本读取 | 就绪延迟、目标端吞吐、校验结果 | 读取未完成版本 |

#### 4.1.6 冷热缓存控制

缓存测试最常见的错误是把操作系统页缓存或残留数据误认为 JuiceFS 热缓存。

每轮测试需要记录并确认：

* JuiceFS 缓存目录和缓存组；
* 测试对象对应数据块是否存在；
* 操作系统页缓存是否影响结果；
* 预热完成状态和预热失败数；
* 缓存命中字节与远端回源字节；
* 测试之间是否有其他任务读取相同数据。

不要在没有证据的情况下把“第二轮更快”直接归因于某一层缓存。

#### 4.1.7 指标计算

```text
应用有效吞吐
= 应用实际消费字节 / 有效读取时间

集群聚合吞吐
= 所有 Worker 应用有效吞吐之和

缓存命中率
= 缓存命中字节 / 客户端请求字节

远端回源比例
= 对象存储读取字节 / 客户端请求字节

数据等待占比
= DataLoader 等待时间 / Step 总时间

预热有效率
= 训练实际命中的预热字节 / 总预热字节
```

对于延迟，应报告样本数、P50、P95、P99 和最大值。对于吞吐，应同时报告稳定区间和峰值，避免只截取短时间峰值。

#### 4.1.8 可确认的性能结论

即使没有具体生产数字，架构仍然给出以下可验证结论：

* 冷缓存必须读取远端数据，因此上界受对象存储、网络和缓存写入共同约束；
* 本地热缓存命中后，读取路径不再依赖对象存储吞吐，上界转向本地 SSD、CPU 和客户端；
* 分布式缓存能减少多节点重复回源，但远端缓存命中仍需要一次节点间网络传输；
* RDMA 只优化分布式缓存的数据传输部分，不能优化对象存储回源、元数据数据库和本地缓存盘；
* 小文件工作负载更容易受请求和元数据延迟影响，大文件顺序吞吐不能代表小文件性能；
* 缓存命中率相同不代表训练收益相同，启动关键路径上的模型权重通常比随机训练分片更敏感；
* 存储峰值吞吐高于训练需求仍不代表通过验收，尾延迟和最慢 Worker 可能拖慢整个同步训练任务。

#### 4.1.9 故障与压力测试

正常路径通过后，还应验证：

* 一个缓存节点退出缓存组；
* 本地缓存盘空间不足或只读；
* 大量任务同时冷启动；
* 对象存储发生限流和短暂错误；
* 元数据数据库连接耗尽或主备切换；
* Mount Pod 被重建；
* 跨云链路中断后恢复；
* Checkpoint 部分 Rank 写入失败；
* 同步完成但内容校验失败。

故障测试不仅记录是否恢复，还需要记录恢复期间的训练错误数、回源流量、尾延迟和恢复时间。

#### 4.1.10 验收标准

最终阈值由具体业务 SLO 决定，但验收结构应保持一致：

| 目标 | 验收方式 |
| --- | --- |
| 训练供数 | 集群有效吞吐持续高于训练消费，数据等待满足训练目标 |
| 模型启动 | 冷、热两种路径都在各自启动预算内 |
| 缓存收益 | 命中率、回源比例与任务时间改善能够相互印证 |
| 元数据 | 目标并发下 P99 和数据库资源仍有余量 |
| Checkpoint | 在保存窗口内提交，失败版本不可被恢复流程选中 |
| 故障降级 | 单节点故障不造成数据丢失，恢复时间满足 SLO |
| 多云就绪 | 目标版本完成 Manifest 校验后才允许训练使用 |
| 成本 | 每次训练或每 TiB 有效读取的容量、请求和流量成本可解释 |

如果测试未达到目标，报告必须指出瓶颈归属和下一步验证，而不是笼统归因于“存储慢”。

#### 4.1.11 结果归档

每次性能评估应产出不可覆盖的报告目录：

```text
performance-reports/
└── 2026-08-13-jfs-cache-evaluation/
    ├── environment.md
    ├── workload.md
    ├── commands.md
    ├── metrics/
    ├── logs/
    ├── results.csv
    └── conclusion.md
```

`conclusion.md` 应回答：

1. 是否满足业务 SLO；
2. 当前主要瓶颈在哪里；
3. 缓存、分布式缓存或 RDMA 是否带来端到端收益；
4. 故障时是否能够安全降级；
5. 结果适用于哪些节点规模和数据格式；
6. 下一次扩容或架构复核的触发条件是什么。

#### 4.1.12 参考工具

JuiceFS 官方提供的基础工具包括：

* [Performance Evaluation Guide](https://juicefs.com/docs/community/performance_evaluation_guide/)；
* [`juicefs bench` 与 `juicefs objbench` 命令参考](https://juicefs.com/docs/community/command_reference/)；
* `juicefs stats` 和 `juicefs profile`，用于观察客户端性能与访问请求。

这些工具适合验证基础链路，但不能替代真实训练、故障注入和端到端成本评估。
