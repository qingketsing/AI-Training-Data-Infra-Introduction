#### 2.6.1 控制平面与数据面

训练数据基础设施可以进一步划分为控制平面和数据面。

```text
                    数据控制平面
      版本、RegionNode、Group、策略、任务与审计
                         │
              ┌──────────┼────────────┐
              ▼          ▼          ▼
          源区域节点   镜像区域节点  镜像区域节点
              │          │            │
              └──── 复制、校验、预热 ────┘
                         │
                         ▼
                       数据面
       对象存储、镜像元数据、缓存、网络与训练集群
```

数据面负责传输和保存真实字节，控制平面负责决定这些字节为什么被处理、处于什么状态以及谁可以使用。二者分离后，复制服务或缓存节点的短暂故障不会破坏权威版本记录；控制平面也不需要成为训练数据吞吐链路的一部分。

控制平面的主要职责包括：

* 管理数据集、模型和 Checkpoint 版本；
* 登记每个“云厂商 × 地区”区域节点及其数据路径；
* 保存 Manifest、Schema、Tokenizer 和血缘信息；
* 编排跨云复制、校验、预热和清理任务；
* 管理用户 Group 对模型、数据集和预热能力的权限；
* 判断版本是否具备训练准入条件；
* 管理幂等、重试、租约和并发限制；
* 提供权限、审批、审计与成本归属；
* 对外提供稳定的查询和操作 API；
* 汇总任务状态，但不替代监控指标系统。

#### 2.6.2 核心资源模型

控制平面至少需要以下逻辑资源。

| 资源 | 作用 | 关键字段 |
| --- | --- | --- |
| RegionNode | 一个云厂商中的一个地区节点 | 云厂商、地区、对象存储、镜像端点、缓存组、状态 |
| Dataset | 一个长期存在的数据集身份 | 名称、负责人、数据域、权限策略 |
| DatasetVersion | 一次不可变数据集发布 | 版本、状态、Manifest、Schema、血缘 |
| Model | 一个长期存在的模型身份 | 名称、负责人、模型族、权限策略 |
| ModelVersion | 一次不可变模型发布 | 版本、状态、权重 Manifest、配置、Tokenizer |
| Artifact | 索引、Tokenizer、评测结果或 Checkpoint | 类型、版本、对象位置、校验值 |
| RegionReplica | 资源版本在一个区域节点中的副本 | 资源版本、区域节点、对象状态、镜像状态、校验状态 |
| MirrorStatus | 源元数据到目标区域的镜像进度 | 源节点、目标节点、源位点、目标位点、延迟、错误 |
| TransferTask | 区域节点间的全量或增量复制 | 源节点、目标节点、资源版本、进度、重试次数 |
| VerificationTask | 数量、大小、哈希或消费校验 | 区域副本、校验级别、结果、错误明细 |
| CacheGroup | 一个区域节点中的缓存池 | 区域节点、成员、容量、网络、隔离级别 |
| UserGroup | 用户和训练任务的权限主体 | 成员、租户、配额、默认策略 |
| GroupResourceBinding | Group 对资源版本的授权 | Group、资源范围、读写动作、有效期 |
| WarmupPolicy | Group 的预热策略 | 可用区域、Cache Group、配额、优先级、过期时间 |
| WarmupTask | 模型或数据集的选择性预热 | Group、区域、资源版本、Manifest、选择范围、状态 |
| TrainingBinding | 训练任务与版本及区域的绑定 | 任务、Group、模型、数据集、区域、短期凭证 |
| RetentionPolicy | 数据保留与删除策略 | 保留期、引用条件、审批策略 |

这些资源应使用稳定的全局 ID。名称可以修改，ID 和已经发布的版本号不能复用。

##### DatasetVersion

`DatasetVersion` 是控制平面的核心。一个版本发布后应保持不可变，任何内容、Schema 或 Tokenizer 变化都创建新版本。

```text
DatasetVersion
├── dataset_id
├── version
├── state
├── manifest_uri
├── manifest_digest
├── schema_version
├── tokenizer_version
├── lineage
├── created_by
└── created_at
```

Manifest 本身也需要校验摘要。如果只校验数据对象而不校验 Manifest，攻击、误操作或并发覆盖仍可能改变版本的实际含义。

`ModelVersion` 使用相同的不可变发布原则。其 Manifest 应明确列出权重分片、配置、Tokenizer、索引及校验值，使模型复制和预热不依赖递归目录扫描。

##### RegionNode 与 RegionReplica

`RegionNode` 是拓扑和调度单元，不代表单台服务器。一个节点可以包含多个训练集群和缓存节点，但只能对应一个明确的云厂商与地区组合。

```text
RegionNode
├── region_node_id
├── cloud_provider
├── region
├── object_storage_endpoint
├── metadata_endpoint
├── cache_group_ids
├── compute_cluster_ids
└── state
```

同一个模型或数据集版本可以在多个区域节点存在副本，但每个 `RegionReplica` 必须独立记录对象、元数据镜像和校验状态：

```text
Dataset v3
├── 云 A / 华北：READY（源节点）
├── 云 A / 华东：READY（镜像节点）
└── 云 B / 华东：VERIFYING（镜像节点）
```

训练任务位于云 B / 华东时，不能因为源节点已经 `READY` 就使用尚在校验的本地副本。训练准入需要同时检查资源版本、目标 `RegionReplica`、Group 权限和必要的预热状态。

##### UserGroup 与资源授权

`UserGroup` 是权限、预热配额和成本归属的主体。授权关系单独保存在 `GroupResourceBinding` 中，不写入模型或数据集本身：

```text
GroupResourceBinding
├── group_id
├── resource_type       # MODEL / DATASET
├── resource_id
├── version_constraint
├── actions             # resource.read / resource.publish / warmup.create
├── region_scope
└── expires_at
```

公共模型可以授权多个 Group 读取并复用物理缓存；敏感数据集可以限制 Group、版本和区域，并使用独立 Cache Group 实现更强隔离。

##### WarmupTask

预热任务只接受 `MODEL` 或 `DATASET` 两种实际资源类型。Group 级预热先根据授权和 `WarmupPolicy` 展开资源清单，再为每个版本创建独立 `WarmupTask`。

任务的幂等键为：

```text
RegionNode + CacheGroup + UserGroup
+ ResourceType + ResourceID + Version + ManifestDigest + Selection
```

同一任务重复提交时复用已有结果；版本、Manifest 或选择的分片发生变化时创建新任务。

#### 2.6.3 状态机

状态机应由控制平面统一执行，不能让复制脚本、人工操作和训练调度系统各自解释状态。

模型和数据集版本可以采用：

```text
DRAFT → PUBLISHING → READY → DEPRECATED → DELETING → DELETED
             │
             └────────→ FAILED ────────→ PUBLISHING
```

各状态含义如下：

* `DRAFT`：允许数据生产任务写入，训练任务不可见；
* `PUBLISHING`：内容冻结，正在生成 Manifest 并执行校验；
* `READY`：校验通过，可以被授权训练任务绑定；
* `FAILED`：发布失败，保留错误明细，修复后可以重试；
* `DEPRECATED`：不再推荐新任务使用，现有引用仍然有效；
* `DELETING`：完成引用检查和保留期后正在清理；
* `DELETED`：数据已经删除，只保留必要的审计记录。

`RegionReplica` 内部需要分别跟踪对象和元数据镜像，两条流不能互相代替：

```text
对象状态：ABSENT → COPYING   → OBJECT_READY
元数据状态：ABSENT → MIRRORING → METADATA_READY
                         │
             两者满足目标版本位点
                         ↓
                     VERIFYING
                      ↙      ↘
                  FAILED     READY
```

预热状态独立于副本状态：

```text
REQUESTED → AUTHORIZED → WAITING_REPLICA → QUEUED
                                         ↓
                                     WARMING
                                         ↓
                                     VERIFYING
                                      ↙      ↘
                                  PARTIAL     WARM

任意执行状态 → FAILED / CANCELLED / EXPIRED
```

`READY` 表示区域副本可以被正确读取，`WARM` 表示指定模型文件或数据集分片已经进入目标缓存。缓存被淘汰后可以从 `WARM` 回到 `EXPIRED` 或重新创建预热任务，但不会改变 `RegionReplica` 的 `READY` 状态。

所有状态迁移必须使用条件更新。例如，只有当前对象状态仍为 `COPYING` 且任务租约属于当前 Worker 时，才能更新为 `OBJECT_READY`。这样可以避免任务超时重试后，旧 Worker 使用过期结果覆盖新状态。

#### 2.6.4 模型与数据集发布流程

模型和数据集使用相同的版本提交边界。一次完整发布流程如下：

```text
数据生产任务写入临时 Prefix
            ↓
关闭写入并生成 Manifest
            ↓
校验对象数量、大小、哈希、Schema 或模型配置
            ↓
登记 DatasetVersion / ModelVersion 和数据血缘
            ↓
版本状态切换为 READY
            ↓
按目标 RegionNode 创建复制与镜像跟踪任务
```

发布接口应接收幂等键。调用方因为超时重复提交时，控制平面返回同一个发布任务，而不是创建两个相互竞争的版本。

推荐的提交顺序是：

1. 数据写入任务专属临时位置；
2. 生成并持久化 Manifest；
3. 校验 Manifest 与对象；
4. 在控制平面事务中登记不可变版本；
5. 最后写入或暴露版本就绪标记；
6. 禁止继续写入已经发布的 Prefix。

对象存储不提供跨多个对象的通用事务，因此版本级状态就是对上层提供的提交边界。

#### 2.6.5 训练准入流程

训练任务不应直接接收任意对象存储路径。任务提交时应指定用户 Group、目标区域节点、模型版本和数据集版本，由控制平面解析实际位置并完成准入检查。

```text
训练请求：Group + RegionNode + ModelVersion + DatasetVersion
                           ↓
               版本是否已经发布为 READY？
                           ↓
              Group 是否具有资源读取权限？
                           ↓
          目标区域的 RegionReplica 是否 READY？
                   ┌───────┴───────┐
                   │               │
                  是               否
                   │               ▼
                   │       创建对象复制与镜像跟踪任务
                   │               ↓
                   │           校验并就绪
                   └───────┬───────┘
                           ↓
             解析 Model / Dataset WarmupPolicy
                           ↓
          模型全量预热 + 数据集选定分片预热
                           ↓
             满足任务要求的 WARM 或阈值？
                           ↓
        创建短期只读凭证和不可变 TrainingBinding
                           ↓
                   允许调度训练 Pod
```

训练绑定应固定 Group、区域节点、模型版本和数据集版本，不能使用 `latest` 之类的可变别名作为最终运行参数。别名只能在任务提交时解析一次，并将解析出的版本写入任务记录。

预热不是所有任务的硬性前提。`WarmupPolicy` 可以规定模型必须达到 `WARM`，而超大数据集只要求首批 Shard Set 完成；如果任务选择跳过可选预热，应在绑定中记录该决策并接受冷读影响。

#### 2.6.6 任务执行与幂等

复制、校验、预热和删除都属于长时间运行任务。控制平面需要支持：

* 幂等任务创建；
* Worker 租约和心跳；
* 进度游标；
* 可重试错误与永久错误分类；
* 指数退避和最大重试次数；
* 取消与超时；
* 死信任务和人工恢复；
* 单个源端、目标端和缓存组的并发限制。

其中，复制任务按 `源 RegionNode + 目标 RegionNode + 资源版本` 幂等；预热任务按 `目标 RegionNode + Cache Group + UserGroup + 资源版本 + 选择范围` 幂等。不同 Group 对同一公共模型的任务可以复用已经存在的物理缓存结果，但权限审计和成本归属仍分别记录。

任务记录保存控制状态，详细的高频指标和日志则进入监控与日志系统。不能把每个对象的实时传输指标都写入控制数据库，否则大规模复制会反过来压垮控制平面。

#### 2.6.7 一致性与并发控制

控制平面的关系型数据需要使用数据库事务保护以下约束：

* 同一数据集的版本号唯一；
* 同一模型的版本号唯一；
* 同一副本只能存在一个活动复制任务；
* `READY` 版本必须关联校验通过的 Manifest；
* `RegionReplica READY` 必须同时满足对象、元数据镜像和区域校验条件；
* `WarmupTask` 的 Group 必须对目标资源版本具有读取权限；
* `WARM` 必须绑定明确的 Manifest 摘要和选择范围；
* 仍被训练任务或模型引用的版本不能删除；
* 状态迁移必须符合状态机；
* 一个租约只能由当前持有者续期或完成。

跨数据库和对象存储无法使用单个本地事务时，应采用可恢复工作流：先记录意图，再执行外部操作，最后提交状态。后台对账任务周期性查找“控制状态与真实对象不一致”的资源并修复。

#### 2.6.8 权限与审计

控制平面自身不应保存长期明文对象存储密钥。用户和任务先归属一个 `UserGroup`，再通过 `GroupResourceBinding` 获得资源权限，并通过 `WarmupPolicy` 获得预热能力。

权限至少拆分为：

* `resource.read`：读取授权的模型或数据集版本；
* `resource.publish`：发布新的模型或数据集版本；
* `warmup.create`：在允许的区域和 Cache Group 创建预热；
* `warmup.admin`：调整优先级、取消任务或跨 Group 管理；
* `checkpoint.write`：写入当前训练任务的输出目录。

训练任务通过工作负载身份或短期凭证访问指定 Prefix，并遵循最小权限：

* 数据生产任务可以写入临时 Prefix；
* 发布任务可以读取临时数据并写入正式版本；
* 训练任务只能读取绑定的数据集和模型版本；
* Checkpoint 任务只能写入当前任务目录；
* 删除任务使用单独角色并要求更严格审批。

预热执行器使用受控服务身份，只能读取任务中已经授权且区域副本为 `READY` 的资源。缓存数据物理存在不代表任意 Group 可以读取；真正的数据访问仍需要通过文件系统权限和训练绑定校验。

审计记录至少包括操作者、时间、资源、原状态、目标状态、请求 ID、审批信息和结果。敏感凭证、个人信息和数据样本内容不能写入审计日志。

#### 2.6.9 可观测性与运行目标

控制平面需要暴露：

* 发布、复制、校验和预热任务的成功率与耗时；
* 每个 RegionNode 的对象复制进度、元数据镜像位点和镜像延迟；
* 各状态资源数量和最长停留时间；
* 任务队列深度、租约超时和重试次数；
* 每个 RegionNode 的就绪版本数量；
* 数据集发布到目标区域就绪的端到端延迟；
* 按模型、数据集和 Group 统计的预热字节、命中率、有效率和淘汰量；
* 各 Group 的预热配额、排队时间和失败原因；
* 训练任务因数据未就绪而等待或拒绝的次数；
* 版本删除前的引用检查结果；
* 按业务、区域和数据集归集的传输字节与成本。

告警应围绕业务结果设计。例如，单个对象重试通常不需要立即通知，但一个正式版本长时间停留在 `VERIFYING`、训练任务无法绑定或目标区域无可用副本时，需要触发告警。

#### 2.6.10 适用边界

数据控制平面解决的是跨组件的生命周期和一致性问题，不应承担以下职责：

* 不代理训练数据的实际读写流量；
* 不替代对象存储的持久化和容灾；
* 不替代 JuiceFS 元数据服务；
* 不替代 Kubernetes 调度器；
* 不把缓存副本提升为权威数据；
* 不用 `WARM` 状态替代区域副本 `READY`；
* 不因为物理缓存共享而绕过 Group 资源授权；
* 不以控制数据库状态替代真实对象校验。

控制平面的最终目标，是让每个训练任务都能回答五个问题：属于哪个 Group、使用什么不可变模型和数据集版本、在哪个 RegionNode 运行、区域副本与预热是否满足策略、出现问题时能否追踪并恢复。
