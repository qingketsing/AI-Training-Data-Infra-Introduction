Remote Storage Layer 是训练数据基座的最终数据持久化层，负责长期保存原始业务数据，清洗和标注后的中间数据，已发布的训练数据集，模型权重，训练 Checkpoint，评测结果和任务产物。

在本文介绍的架构中，远端存储主要由云厂商提供的对象存储承担。对象存储具有容量扩展简单、数据可靠性高、成本较低和适合保存大规模非结构化数据等特点，因此适合作为 AI 数据基座的最终存储介质。

但是，对象存储与训练程序常用的文件系统接口存在明显差异。训练框架通常希望通过目录、文件路径和随机读取的方式访问数据，而对象存储主要通过对象键和 API 提供访问能力。

因此，Remote Storage Layer 的设计重点不仅是选择对象存储，还应当包括：目录组织，数据分桶，多云数据同步和一致性，单个大文件和海量小文件的访问差异。

对象存储负责数据的持久化和可靠性，但不会单独承担训练节点的高性能数据读取需求。训练节点与对象存储之间仍然需要缓存和文件系统层进行加速。

#### 2.2.1 职责与设计目标

Remote Storage Layer 是 AI 训练数据基座中的持久化存储层。它位于整个训练数据访问链路的底部，负责长期、可靠地保存训练数据、模型权重、Checkpoint 和任务产物，并作为其他缓存副本和计算副本的最终数据来源。

在典型架构中，Remote Storage 通常被视为数据的 Source of Truth。上层缓存中的数据可以被淘汰、失效或者重新构建，但远端存储中的正式数据必须保持完整、可靠且可追踪。

```text
               Source of Truth
                      │
                      ▼
              Remote Storage
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
      节点缓存                 计算节点副本
          │                       │
          └───────────┬───────────┘
                      ▼
                 训练任务消费
```

Remote Storage Layer 的主要职责包括以下几个方面。

##### 数据持久化

Remote Storage 需要长期保存 AI 训练过程中产生的不同类型数据，包括：

* 原始业务数据；
* 清洗、标注和增强后的中间数据；
* 正式发布的训练数据集；
* 模型权重；
* 训练 Checkpoint；
* 评测数据和评测结果；
* 数据处理及训练任务的最终产物。

不同类型的数据具有不同的生命周期和访问频率。正式数据集和最终模型权重通常需要长期保留，而部分中间数据和临时 Checkpoint 可以按照生命周期策略进行清理。

##### 统一数据源

在多集群、多节点或者多云环境中，同一份数据可能产生多个缓存和计算副本。Remote Storage 需要提供统一的数据来源，避免不同计算环境各自维护一套相互独立的数据副本。

```text
                  Remote Storage
                  Dataset v3
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
    GPU 集群 A      GPU 集群 B      数据处理集群
```

训练任务应当绑定明确的数据集版本，而不是依赖某台节点上临时存在的本地文件。即使本地缓存被清空，系统也能够根据远端存储重新恢复数据。

##### 数据可靠性

训练数据和模型权重往往需要较高的可靠性。如果数据丢失，不仅会导致训练任务失败，还可能使已经完成的数据清洗、标注和训练工作无法复现。

因此，Remote Storage 需要具备：

* 数据冗余；
* 故障恢复；
* 数据完整性校验；
* 版本保护；
* 误删除防护；
* 备份与归档；
* 跨可用区或者跨地域容灾能力。

Remote Storage 的设计重点通常不是追求最低的单次访问延迟，而是保证数据在节点、磁盘或部分服务发生故障后仍然可以恢复。

##### 容量扩展

AI 训练数据通常会持续增长。除了原始数据外，清洗结果、数据集版本、模型权重和 Checkpoint 也会不断占用新的存储空间。

Remote Storage 应尽可能支持容量的弹性扩展，使系统不需要频繁迁移已有数据或者重新设计存储集群。

对于自建存储系统，扩容通常意味着增加磁盘和存储节点，并处理数据再平衡；对于托管对象存储，容量管理通常由云厂商完成，使用方主要关注费用、配额和访问性能。

##### 多节点并发访问

训练和数据处理任务通常会同时从多个节点访问相同数据。Remote Storage 需要支持较高的并发读取能力，并避免单个训练任务独占整个存储服务。

需要重点考虑的访问模式包括：

* 多个训练节点读取同一个模型权重；
* 多个 Worker 并行读取不同的数据分片；
* 多个训练任务同时访问同一数据集；
* 数据处理任务持续写入新的中间结果；
* Checkpoint 周期性并发写入。

Remote Storage 不一定直接满足所有高性能访问需求，但必须能够作为缓存未命中时的稳定后端，并承受一定规模的突发请求。

##### 接口与生态兼容

Remote Storage 需要能够被上层数据处理、文件系统和训练框架访问。

常见接口包括：

* S3 兼容 API；
* 云厂商对象存储 SDK；
* HTTP API；
* HDFS 接口；
* NFS 或其他文件访问协议；
* 通过 FUSE、CSI 或分布式文件系统间接访问。

在当前云原生 AI 基础设施中，S3 兼容接口具有较强的通用性。许多数据处理框架和分布式文件系统都可以将兼容 S3 API 的存储服务作为后端。

不过，接口兼容并不代表不同产品的行为完全一致。实际选型时仍需要验证权限机制、分片上传、List 操作、错误处理、限流和一致性语义。

##### 安全与访问控制

Remote Storage 通常保存企业内部数据和模型资产，因此需要提供严格的权限控制。

主要包括：

* 按 Bucket、Prefix 或数据集进行权限隔离；
* 使用临时凭证而不是长期静态密钥；
* 控制训练任务的读写范围；
* 对敏感数据进行加密；
* 记录数据访问日志；
* 限制跨账号和跨云访问；
* 防止训练任务覆盖正式数据；
* 对生产数据和测试数据进行隔离。

训练任务通常只需要读取已发布的数据集，不应默认拥有修改原始数据和历史数据集的权限。

##### 成本控制

Remote Storage 的成本不仅包括存储容量费用，还可能包括：

* API 请求费用；
* 跨地域流量费用；
* 公网或跨云流量费用；
* 数据取回费用；
* 自建存储的机器和磁盘成本；
* 运维、监控和故障处理成本；
* 数据冗余带来的额外容量开销。

对于 AI 训练场景，数据可能会被反复读取。如果每次训练都直接从远端对象存储读取全部数据，网络流量和请求成本可能持续增加。因此，Remote Storage 通常需要与上层缓存系统共同设计。

##### Remote Storage 的设计目标

综合来看，Remote Storage Layer 的主要设计目标可以概括为：

1. **可靠性**：数据发生局部故障后仍然能够恢复；
2. **可扩展性**：能够承载持续增长的数据规模；
3. **统一性**：为不同集群和训练任务提供统一的数据来源；
4. **可追踪性**：能够关联数据来源、版本和生命周期；
5. **兼容性**：可以被主流数据处理和训练系统访问；
6. **安全性**：确保数据只被经过授权的任务使用；
7. **成本可控**：在容量、请求、流量和运维成本之间取得平衡；
8. **可恢复性**：上层缓存或计算副本丢失后可以重新构建。

Remote Storage 的主要目标并不是直接提供类似本地磁盘的低延迟访问，也不一定需要完整支持 POSIX 文件系统语义。低延迟读取、文件目录抽象和重复数据访问加速，通常由上层 FileSystem Layer 和 Cache Layer 负责。

#### 2.2.2 对象存储类型与选型标准

对象存储是 Remote Storage Layer 中最常见的实现方式之一。它通常使用 Bucket 组织数据，并通过唯一的 Object Key 标识每个对象。

与传统文件系统不同，对象存储主要围绕对象的上传、下载、删除和查询提供能力，而不是直接提供完整的文件目录、随机写入和文件锁语义。

```text
Bucket
├── raw/web/2026/07/data-001.parquet
├── datasets/sft/v3/train-001.parquet
├── models/model-a/v5/model.safetensors
└── checkpoints/job-1024/step-5000/
```

根据部署和维护方式，对象存储可以分为云厂商托管对象存储和自建对象存储两类。

##### 云厂商托管对象存储

托管对象存储由云厂商负责底层存储节点、数据冗余、容量扩展和服务可用性。使用方通常只需要创建 Bucket、配置权限，并通过 API 或 SDK 访问数据。

常见服务包括：

| 类型    | 常见服务示例                                            |
| ----- | ------------------------------------------------- |
| 国际云厂商 | Amazon S3、Google Cloud Storage、Azure Blob Storage |
| 国内云厂商 | 阿里云 OSS、火山引擎 TOS、腾讯云 COS、华为云 OBS                  |

托管对象存储的主要优点包括：

* 不需要自行管理磁盘和存储节点；
* 容量可以按需增长；
* 通常具有较完善的数据冗余和容灾能力；
* 与云厂商的计算、权限和网络体系集成较好；
* 支持生命周期、版本控制和跨地域复制等功能；
* 适合团队运维资源有限的场景。

其主要限制包括：

* 长期使用可能产生较高的存储和请求费用；
* 跨区域和跨云访问可能产生较高流量成本；
* 性能受到云厂商限流、网络和服务配额影响；
* 容易形成对特定云厂商的依赖；
* 部分高级能力和权限模型存在产品差异；
* 业务无法直接控制底层存储节点和数据布局。

对于主要运行在单一云厂商上的训练集群，使用同一云厂商的对象存储通常能够降低网络复杂度和跨云流量成本。

##### 自建对象存储

自建对象存储由企业自行部署和维护。常见方案包括：

* MinIO；
* Ceph RGW；
* 其他提供 S3 兼容接口的分布式存储系统。

自建对象存储的主要优点包括：

* 可以控制数据实际存放的位置；
* 可以根据业务需求选择磁盘、网络和冗余策略；
* 适合本地数据中心、私有云或合规要求较高的场景；
* 在数据量稳定且访问频繁时，可能降低长期云服务费用；
* 可以减少对单一云厂商的依赖；
* 能够在本地高速网络中为计算集群提供数据服务。

其主要限制包括：

* 需要自行管理磁盘、节点、扩容和故障恢复；
* 需要持续维护监控、告警、升级和容量规划；
* 存储节点故障可能触发较大规模的数据恢复；
* 扩容和数据再平衡会消耗网络及磁盘资源；
* 数据可靠性取决于实际部署和运维水平；
* 小规模集群可能无法充分发挥分布式存储的优势。

自建对象存储并不代表一定比云对象存储成本更低。如果数据规模较小、团队缺少存储运维经验或者计算资源本身具有较强弹性，自建存储的机器和人力成本可能高于托管服务。

##### 托管对象存储与自建对象存储的基本比较

| 维度     | 托管对象存储           | 自建对象存储           |
| ------ | ---------------- | ---------------- |
| 容量扩展   | 通常自动扩展           | 需要增加节点和磁盘        |
| 运维成本   | 较低               | 较高               |
| 底层控制能力 | 较弱               | 较强               |
| 初期建设成本 | 较低               | 较高               |
| 长期成本   | 与容量、请求和流量相关      | 与硬件、机房和人力相关      |
| 数据位置   | 由云服务区域决定         | 可以自行控制           |
| 故障处理   | 主要由云厂商负责         | 由使用方负责           |
| 云生态集成  | 较好               | 需要自行适配           |
| 跨云能力   | 可能受流量和产品绑定影响     | 接口可控，但仍需建设同步链路   |
| 适用场景   | 云上业务、快速上线、有限运维团队 | 私有化、本地集群、强数据控制需求 |

##### 对象存储的选型维度

对象存储选型不能只比较存储单价或厂商品牌，而应当从实际工作负载出发进行分析。

###### 数据规模与增长速度

首先需要估算：

* 当前数据总量；
* 每日或每月新增数据量；
* 数据保留周期；
* 数据集版本数量；
* Checkpoint 和模型权重的增长速度；
* 是否需要保存多个副本。

如果数据规模增长较快，应优先考虑容量扩展简单、生命周期管理完善的方案。

###### 对象数量与平均大小

相同的数据总量可能对应完全不同的存储压力：

```text
场景 A：1 PB 数据，由 1,000 个大对象组成
场景 B：1 PB 数据，由 10 亿个小对象组成
```

大量小对象会增加：

* 请求数量；
* List 和元数据操作压力；
* 网络连接开销；
* 文件系统映射成本；
* 数据扫描和同步复杂度。

因此，选型时不仅要关注容量，还要关注对象数量、平均大小和大小分布。

###### 访问模式

需要明确数据主要以何种方式被访问：

* 大文件顺序读取；
* 小文件随机读取；
* 多节点并发读取；
* 数据写入一次、读取多次；
* 频繁覆盖和更新；
* 按数据集版本整体读取；
* 只读取对象中的部分范围；
* 周期性写入 Checkpoint。

对象存储更适合对象级别的写入和读取，不适合频繁修改同一对象中的少量内容。需要高频随机写入的场景，可能需要引入文件系统、块存储或专门的中间存储层。

###### 性能与网络距离

需要评估对象存储与计算集群之间的网络关系：

```text
同地域同云访问
同云跨地域访问
跨云访问
公网访问
本地数据中心访问云对象存储
```

距离越远，通常意味着更高的延迟、更低的稳定吞吐以及更高的流量成本。

对于训练任务而言，需要重点验证：

* 单节点读取吞吐；
* 多节点聚合吞吐；
* 首字节延迟；
* 并发请求能力；
* 大文件读取性能；
* Range Read 性能；
* 训练高峰期的稳定性；
* 服务限流和配额。

###### 可靠性与容灾需求

需要明确系统可以容忍的数据丢失范围和恢复时间，例如：

* 是否允许单个可用区故障影响训练；
* 是否需要跨地域副本；
* 是否需要对象版本控制；
* 是否需要防止误删除；
* 数据损坏后如何发现；
* 是否需要离线备份；
* 需要多长时间完成数据恢复。

并非所有数据都需要相同等级的保护。正式数据集和最终权重可以使用较高可靠性策略，而可以重新生成的中间数据可以采用成本更低的存储策略。

###### 一致性与数据可见性

对象写入完成后，训练任务何时能够读取到新数据，是数据集发布流程中的重要问题。

选型时需要验证：

* 新对象写入后的可见性；
* 对象覆盖后的读取行为；
* 删除操作的传播；
* List 结果是否及时更新；
* 跨地域复制的延迟；
* 多云同步完成后如何确认数据就绪。

在训练数据基座中，通常不应只依赖“文件已经出现”来判断数据集可以使用，而应通过 Manifest、版本状态或发布标记确认整个数据集已经完整写入。

###### 接口和生态兼容性

需要检查对象存储是否能够被现有系统稳定访问，例如：

* 是否兼容 S3 API；
* 是否支持当前使用的数据处理框架；
* 是否可以作为 JuiceFS 等文件系统的数据后端；
* 是否支持 Kubernetes CSI 或相应挂载方式；
* SDK 是否覆盖主要开发语言；
* 是否支持 Multipart Upload 和 Range Read；
* 权限、签名和临时凭证是否容易集成。

S3 兼容性需要通过实际测试确认，不能只根据产品声明判断。

###### 安全与合规

对于企业业务数据，需要考虑：

* 数据是否允许进入公有云；
* 数据必须保存在哪个地域；
* 是否需要服务端或者客户端加密；
* 是否需要审计日志；
* 是否支持细粒度权限；
* 是否支持密钥托管；
* 是否需要私网访问；
* 是否需要隔离不同业务和租户。

如果数据具有严格的本地保存要求，自建对象存储或者私有化部署可能比公共云服务更合适。

###### 成本

完整成本应包括：

```text
总成本 =
存储容量费用
+ 请求费用
+ 数据读取费用
+ 跨区域或跨云流量费用
+ 缓存成本
+ 存储节点成本
+ 运维人力成本
+ 故障恢复成本
```

托管对象存储的费用通常更容易在早期控制，但随着数据量、请求量和跨云流量增长，长期费用可能显著增加。

自建对象存储可以减少部分云服务费用，但会引入服务器、磁盘、网络、机房和运维成本。两种方案需要基于较长周期的总拥有成本进行比较。

##### 基本选型原则

对象存储不存在适用于所有场景的统一最优解，可以按照以下原则进行初步选择：

```text
云上业务、快速上线、运维能力有限
→ 优先考虑云厂商托管对象存储

私有化部署、数据不能离开本地
→ 考虑自建对象存储

计算集群和数据位于同一云
→ 优先选择同云同地域的对象存储

存在多个云计算集群
→ 明确主数据源，并建设复制和版本就绪机制

数据被频繁重复读取
→ 在远端存储之上增加文件系统和缓存层

存在海量小文件
→ 优先优化数据格式和打包方式，再评估文件系统抽象
```

对象存储选型的本质不是选择功能最多的产品，而是在可靠性、性能、成本、运维复杂度、生态兼容和数据控制能力之间进行权衡。

选型结果还需要通过实际业务数据进行验证，尤其是多节点并发读取、大文件和小文件访问、跨云传输以及缓存未命中场景下的性能表现。

#### 2.2.3 对象存储的部署形态与访问方式

对象存储可以按照部署方式分为云厂商托管对象存储和企业自建对象存储。无论采用哪种部署方式，上层应用通常都通过对象存储 API、SDK 或者文件系统抽象层访问其中的数据。

##### S3 API 直接访问

S3 API 是当前对象存储中较为通用的访问接口。应用程序可以通过 SDK、命令行工具或者 HTTP 请求直接执行对象的上传、下载、查询和删除操作。

```text
训练或数据处理程序
        ↓
    S3 SDK / API
        ↓
      对象存储
```

直接通过 S3 API 访问对象存储具有链路简单、依赖较少和适合批量数据处理等优点。Ray Data、Spark 和部分训练框架可以直接读取对象存储中的数据。

但是，对象存储 API 与传统文件系统接口存在差异。部分依赖 POSIX 文件路径、随机访问、目录操作或者文件锁的程序，通常无法直接使用对象存储，需要通过文件系统层进行适配。

##### 云厂商托管对象存储

云对象存储由云厂商负责底层硬件、容量扩展、数据冗余和故障恢复。常见服务包括 Amazon S3、阿里云 OSS、火山引擎 TOS 和腾讯云 COS。

云对象存储适合以下场景：

* 训练和数据处理任务主要运行在公有云中；
* 数据规模持续增长；
* 团队不希望自行维护存储集群；
* 需要较高的数据可靠性和可用性；
* 需要使用生命周期、版本控制和跨地域复制等能力。

在单云环境中，计算集群通常优先选择同地域的对象存储，以减少网络延迟和跨地域流量成本。

##### MinIO

MinIO 是一种提供 S3 兼容接口的对象存储系统，可以部署在企业自己的服务器、裸金属集群或者 Kubernetes 环境中。

MinIO 的优势是部署方式相对直接，并且能够为本地计算集群提供统一的 S3 访问接口。它适合私有化部署、本地数据中心以及需要自行控制数据位置的场景。

但是，自建 MinIO 需要企业自行承担：

* 磁盘和存储节点管理；
* 数据冗余；
* 容量扩展；
* 故障恢复；
* 监控和告警；
* 软件升级；
* 数据备份。

因此，在缺少独立存储节点或者存储运维能力有限的场景中，自建 MinIO 不一定比使用云对象存储更合适。

##### Ceph RGW

Ceph 是一种分布式存储系统，可以提供块存储、文件存储和对象存储能力。其中，Ceph RGW，即 RADOS Gateway，负责向上层提供兼容 S3 或 Swift 的对象存储接口。

```text
应用程序
    ↓
S3 API
    ↓
Ceph RGW
    ↓
Ceph RADOS 存储集群
```

Ceph RGW 适合已经建设 Ceph 集群，或者同时需要块、文件和对象存储能力的企业。相比单独部署对象存储，Ceph 能够提供更加完整的分布式存储体系，但其部署、扩容、故障恢复和日常运维也更加复杂。

因此，Ceph RGW 通常更适合具有较大数据规模、稳定基础设施和专业存储运维团队的场景。

不同部署形态可以简单概括为：

```text
快速上线、降低运维成本
→ 云厂商托管对象存储

私有化部署、需要 S3 兼容接口
→ MinIO

已有 Ceph 基础设施或需要统一存储体系
→ Ceph RGW
```

对象存储的部署方式并不直接决定训练任务最终采用的访问接口。训练程序既可以通过 S3 API 直接读取对象，也可以通过 JuiceFS 等文件系统层间接访问对象存储。

#### 2.2.4 对象键组织、命名空间与数据分桶

对象存储通常使用 Bucket 作为顶层数据容器，并使用 Object Key 唯一标识其中的每一个对象。

对象存储并不存在与传统文件系统完全相同的真实目录。用户看到的目录结构，通常是由 Object Key 中的前缀模拟出来的。

例如：

```text
s3://ai-data/datasets/sft/v3/train-0001.parquet
```

其中：

```text
ai-data
→ Bucket

datasets/sft/v3/
→ Object Key Prefix

train-0001.parquet
→ 对象名称
```

合理的数据组织方式能够降低权限管理、数据同步、生命周期管理和问题排查的复杂度。

##### 数据分桶

不同类型、不同权限或者不同生命周期的数据可以使用不同的 Bucket 进行隔离。例如：

```text
ai-raw-data
→ 原始业务数据

ai-processed-data
→ 清洗和标注后的中间数据

ai-datasets
→ 正式发布的训练数据集

ai-models
→ 模型权重和 Tokenizer

ai-checkpoints
→ 训练 Checkpoint
```

是否需要拆分多个 Bucket，应根据以下因素决定：

* 数据权限是否不同；
* 数据生命周期是否不同；
* 是否由不同团队维护；
* 是否需要独立配置访问策略；
* 是否需要跨云同步；
* 是否需要分别统计容量和成本。

Bucket 数量不宜无限增加。对于权限和生命周期相近的数据，也可以放在同一个 Bucket 中，通过不同 Prefix 进行逻辑隔离。

##### 对象键与命名空间

Object Key 应尽量能够表达数据的业务类型、版本和时间范围。例如：

```text
datasets/
└── customer-service-sft/
    └── v3/
        ├── train/
        │   ├── part-0001.parquet
        │   └── part-0002.parquet
        ├── validation/
        └── test/
```

模型权重可以按照模型名称和版本进行组织：

```text
models/
└── customer-service-model/
    └── v5/
        ├── config.json
        ├── tokenizer.json
        └── model-00001.safetensors
```

Checkpoint 则可以按照训练任务和训练步骤组织：

```text
checkpoints/
└── training-job-1024/
    ├── step-1000/
    ├── step-2000/
    └── step-3000/
```

设计命名空间时，应尽量满足以下要求：

* 路径含义清晰；
* 数据集版本明确；
* 临时数据与正式数据隔离；
* 不直接覆盖已经发布的版本；
* 便于按 Prefix 设置权限；
* 便于执行批量同步和生命周期清理；
* 不在对象键中保存密码、用户隐私等敏感信息。

对于正式数据集，通常应采用不可变版本设计。数据集发布后不再直接修改原有对象，而是生成新的版本：

```text
datasets/sft/v1/
datasets/sft/v2/
datasets/sft/v3/
```

这样可以避免训练过程中读取到正在发生变化的数据，也有利于训练复现、问题定位和版本回滚。

在多云场景中，稳定的 Bucket 与 Object Key 规范还可以作为不同对象存储之间的数据映射基础。同步系统可以根据 Bucket、Prefix 和数据集版本判断需要复制的数据范围，而不需要逐个理解对象的业务内容。


#### 2.2.5 多云数据复制、同步与一致性校验

当 GPU 资源分布在多个云或多个地域时，让所有训练任务跨云读取同一个对象存储，通常会同时引入网络抖动、访问延迟、出口带宽上限和跨云流量费用。更稳定的方式是确定唯一的权威数据源，再把已经发布的数据集和模型版本复制到计算集群附近。

```text
                         主对象存储
                        Source of Truth
                              │
               ┌──────────────┴──────────────┐
               │                             │
               ▼                             ▼
        云 A 对象存储副本               云 B 对象存储副本
               │                             │
               ▼                             ▼
          GPU 集群 A                    GPU 集群 B
```

复制链路应当采用单写多读模型。主存储是唯一写入源，目标存储只保存可重建的只读副本。训练任务绑定明确的数据集版本，不直接读取一个持续变化的 Prefix。

##### 复制单位

同步系统不应把“整个 Bucket”作为唯一复制单位。更合适的复制边界是一个不可变的数据集版本、模型版本或 Checkpoint 版本：

```text
datasets/customer-service-sft/v3/
├── data/
├── manifest.json
└── _READY
```

其中 `manifest.json` 描述该版本包含的对象，至少记录：

* 逻辑路径和对象键；
* 对象大小；
* 内容校验值或可信的对象校验信息；
* 数据格式与分片数量；
* 数据集版本和生成流水线版本；
* 创建时间与发布者；
* 上游数据版本；
* 可选的 Tokenizer 和 Schema 版本。

Manifest 是校验和审计的依据，`_READY` 则是完成复制及校验后的发布标记。`_READY` 必须最后写入，不能与数据对象同时创建。

##### 全量与增量同步

全量同步适合第一次建立目标副本、增加新训练地域或灾难恢复后的副本重建。执行时应以版本 Prefix 为范围，并记录扫描到的对象数、字节数、成功数、失败数和校验结果。

完成第一次全量同步后，日常链路应采用增量同步。增量判断可以依据不可变版本、Manifest、对象校验值、变更日志或上次成功游标。对于正式数据集，推荐只新增版本而不覆盖旧对象，这样增量同步就可以简化为复制目标端尚不存在的新版本。

```text
第一次复制：v1 + v2 + v3
后续复制：只复制新发布的 v4
```

如果业务必须覆盖对象，不能只比较修改时间。不同对象存储的时间精度、Multipart Upload 产生的 ETag 语义和跨云时钟可能不同，应优先使用业务生成的内容哈希或 Manifest 中的校验信息。

##### 触发方式

同步任务可以通过三种方式触发：

* **事件触发**：数据集发布、模型产出或训练任务提交后立即创建同步任务，延迟最低；
* **定时触发**：周期性扫描新版本，适合作为事件丢失后的兜底；
* **人工触发**：用于历史版本迁移、故障恢复和指定版本重试。

生产系统通常同时保留事件触发和定时对账：事件链路负责及时性，定时链路负责最终收敛。人工触发必须复用同一个幂等任务接口，不能绕过校验和审计流程。

##### 版本状态机

对象出现在目标存储中，并不代表整个版本已经能够使用。同步过程需要显式状态机：

```text
DRAFT
  ↓ 发布请求
COPYING
  ↓ 对象复制完成
VERIFYING
  ↓ 校验通过
READY

COPYING / VERIFYING
  ↓ 不可恢复错误
FAILED
  ↓ 修复后重试
COPYING
```

训练调度系统只允许消费 `READY` 版本。`FAILED` 版本不得通过手工创建 `_READY` 的方式绕过校验。旧的 `READY` 版本在新版本复制失败时继续可用，从而避免同步故障扩大为全部训练任务不可用。

##### 一致性校验

校验应由低成本到高成本分层进行：

1. **版本级校验**：确认 Manifest、版本号和发布状态一致；
2. **数量校验**：比较源端与目标端对象数量；
3. **大小校验**：比较每个对象及版本总字节数；
4. **内容校验**：比较内容哈希或可信的对象校验值；
5. **抽样读取**：从目标端实际打开一部分数据分片和模型文件；
6. **消费校验**：使用真实 DataLoader 或模型加载器执行最小读取任务。

数量和大小相同只能发现部分问题，不能证明内容完全一致。正式发布前至少应对 Manifest 中的全部对象执行确定性的内容校验；超大规模数据也可以在复制阶段逐对象校验，并在发布阶段核对汇总结果。

##### 幂等、重试与限流

同步任务的幂等键可以由以下字段组成：

```text
源存储 + 目标存储 + 资源类型 + 版本号
```

同一个幂等键只能存在一个活动任务。失败对象使用指数退避和随机抖动重试；权限错误、目标容量不足或 Manifest 损坏等永久错误应立即转为 `FAILED`，避免无限重试。

同步服务还需要限制 List、GET 和 PUT 的并发度。并发过低会浪费专线带宽，并发过高则可能触发对象存储限流、挤占训练读取带宽或产生意外费用。限流参数应按源端、目标端和网络链路分别配置。

##### 冲突与删除

多云副本不应允许双向任意写入。若两个云同时修改同一版本，仅凭“最后写入时间”很难可靠解决冲突，也会破坏训练复现。

推荐规则如下：

* 已发布版本不可修改；
* 主存储是唯一写入源；
* 目标副本默认只读；
* 修订数据时发布新版本；
* 删除采用延迟回收，不立即传播物理删除；
* 清理前确认没有训练任务、模型和审计记录继续引用该版本。

删除可以先将版本标记为 `DEPRECATED`，经过保留期后再进入 `DELETING`，最终删除对象。这样能够为误操作、回滚和同步延迟保留恢复窗口。

##### 灾难恢复

多云副本是否能够承担容灾职责，需要提前定义 RPO 和 RTO：

* RPO 决定最多可以接受多少尚未复制的数据；
* RTO 决定主存储故障后多长时间内恢复训练读取；
* 切换流程需要同时处理对象数据、访问凭证、Endpoint 和元数据服务；
* 定期恢复演练要验证从副本挂载、数据集校验到训练启动的完整链路。

仅复制对象数据并不能自动解决文件系统元数据的跨云延迟或丢失问题。使用 JuiceFS 等数据与元数据分离的文件系统时，需要分别设计对象数据复制和元数据高可用、备份或镜像方案。

#### 2.2.6 对象大小与访问模式

存储容量相同并不代表训练时的访问压力相同。对象大小、读取顺序、并发度和复用次数，会共同决定对象存储请求数、元数据压力、缓存收益和训练等待时间。

##### 大文件顺序读取

模型权重、Parquet 分片和 WebDataset 归档通常以较大的连续对象保存。大文件顺序读取具有以下特点：

* 单次请求能够传输更多有效数据；
* 容易通过 Range Read 和预读实现并行；
* 对象请求数相对较少；
* 更容易利用网络和本地 SSD 的顺序吞吐；
* 单个对象过大时，失败重试和任务分片粒度会变粗。

分片大小不应只追求越大越好。合理的分片应使多个 Worker 能够并行读取，同时避免产生海量对象。具体大小需要根据样本大小、Worker 数量、对象存储吞吐和失败重试成本实测确定。

##### 海量小文件

如果数亿条样本分别保存为独立 JSON 或图片小文件，即使总容量不大，也会产生大量文件打开、List、HEAD、GET 和元数据查询操作。

```text
一亿个 10 KiB 对象
→ 容量约 1 TiB
→ 但可能需要一亿次对象读取请求
```

小文件场景的首要优化通常不是增加缓存，而是改变数据布局：

* 将结构化样本写入 Parquet 或 Arrow；
* 将图片、音频等样本打包为 WebDataset 或其他归档分片；
* 为归档建立索引，避免读取无关数据；
* 控制每个分片的样本数和总大小；
* 避免训练时递归 List 整个数据集；
* 使用 Manifest 直接给出训练分片列表。

打包后需要保留样本级索引和血缘，否则问题样本定位、增量更新和局部重建会变得困难。

##### 随机读取

随机读取会降低预读效果，并增加 Range Read 和缓存数据块的离散程度。若训练任务只读取每个大对象中的少量内容，需要确认数据格式支持索引和范围访问，而不是每次下载整个对象。

可以从以下方向优化：

* 按训练访问局部性重新组织分片；
* 使用支持列裁剪、行组过滤或样本索引的数据格式；
* 让 DataLoader 在分片内部顺序读取，在分片之间随机打乱；
* 将真正高频的索引和小型元数据放在低延迟存储中；
* 评估缓存块大小，避免一次随机读取带入过多无用数据。

##### 多节点高并发读取

分布式训练启动时，大量节点可能同时读取同一份模型权重，形成典型的惊群流量：

```text
N 个节点同时启动
       ↓
同一组模型对象
       ↓
对象存储与出口链路瞬时高并发
```

这一场景适合采用错峰启动、缓存预热、本地缓存或分布式缓存。若各 Worker 读取不同的数据分片，则应保证分片数量不少于并行 Worker 数量，并避免所有分片共享单个热点索引或目录操作。

训练读取所需的有效带宽可以先用近似模型估算：

```text
训练有效读取带宽 = 每个 Worker 的样本消费速率 × Worker 数量
远端回源带宽 ≈ 训练有效读取带宽 × (1 - 缓存命中率)
```

这个估算没有计入压缩、预取放大、重复读取和协议开销，生产容量规划还需要使用真实数据格式和 DataLoader 校准。

##### Checkpoint 与写入模式

Checkpoint 与训练数据读取具有不同特征：多个 Rank 可能在同一时间写入大量分片，并在保存完成后要求形成一致的恢复点。

需要关注：

* 每次 Checkpoint 的总大小；
* 保存周期和允许的最大阻塞时间；
* 并发写入对象数；
* 临时文件到正式版本的提交方式；
* 失败后半成品清理；
* 多个 Checkpoint 的保留策略；
* 是否需要异步上传和本地暂存。

Checkpoint 应先写入任务专属的临时版本，全部 Rank 完成并校验后再提交为可恢复版本。不能仅以某个目录存在作为保存成功的判断依据。

##### 请求数量与成本

对象存储成本除了容量和流量，还包括 API 请求。可以使用下式进行初步估算：

```text
月度请求成本
≈ GET 请求数 × GET 单价
+ PUT 请求数 × PUT 单价
+ LIST/HEAD 请求数 × 对应单价
```

缓存能够减少重复 GET 和跨云流量，但也会引入 SSD、缓存节点和运维成本。是否启用缓存应基于复用次数和命中率评估：只读取一次的数据通常难以摊薄预热和缓存写入成本，频繁重复读取的模型权重与热门数据集更容易受益。

##### 访问模式与推荐策略

| 访问模式 | 主要瓶颈 | 优先策略 |
| --- | --- | --- |
| 大文件顺序读取 | 网络与对象存储吞吐 | 合理分片、并发读取、预读与缓存 |
| 海量小文件 | 请求数与元数据操作 | 数据打包、Manifest、减少 List |
| 随机范围读取 | 首字节延迟与读放大 | 索引、范围读取、调整数据布局 |
| 多节点读取同一模型 | 突发回源与热点 | 预热、分布式缓存、错峰启动 |
| 多 Worker 读取不同分片 | 聚合吞吐与分片调度 | 增加分片、均匀分配、控制并发 |
| 周期性 Checkpoint 写入 | 突发写入与提交一致性 | 临时版本、原子发布、保留策略 |


#### 2.2.7 远端存储层的局限

Remote Storage 是可靠的持久化底座，但不能独立满足训练系统的全部访问需求。

| 局限 | 对训练的影响 | 常见缓解方式 |
| --- | --- | --- |
| 不提供完整 POSIX 语义 | 依赖路径、Rename 或文件锁的程序需要改造 | 引入文件系统层，或让应用直接使用对象 API |
| 小对象固定开销明显 | 请求数、首字节延迟和费用上升 | 将样本打包为较大的训练分片 |
| 不适合小范围频繁覆盖 | 写放大且提交语义复杂 | 使用不可变对象和版本化发布 |
| 网络距离不可忽略 | 冷启动和缓存未命中时训练等待 | 同地域部署、副本复制、缓存预热 |
| 重复读取成本高 | 多节点反复产生 GET 和跨云流量 | 本地缓存或分布式缓存 |
| List 不能代替事务 | 训练可能看到同步一半的数据集 | Manifest、状态机与 `_READY` 标记 |
| 服务配额和限流 | 高峰期吞吐下降或请求失败 | 并发控制、重试、容量评估和监控 |
| 多云复制是异步过程 | 目标端存在版本滞后 | 版本就绪校验和明确的 RPO/RTO |

因此，Remote Storage 的边界应当保持清晰：它负责权威数据、持久化、容量和恢复；Filesystem Layer 负责统一访问语义；Cache Layer 负责降低重复远程读取；数据控制平面负责版本、复制、发布和训练准入。只有这些职责协同工作，对象存储才能成为稳定的 AI 训练数据基座。
